# SFAD Threat — 認可マトリクス + データ分類

機能仕様（functional spec）を入力に、**セキュリティ仕様** を独立した artifact として出力するスキル。
Discovery で「認証が必要か・誰が使うか」までは確認済み。ここでは攻撃者視点の論点（認可・IDOR・Mass Assignment）を**実装前に表として確定する**。

## 何を防ぐか

このスキルは以下の事故を **仕様段階で** 防ぐ:

- 認可ゼロ API（誰でも他人のリソースを操作できる）
- IDOR（他人のリソース ID を指定して操作できる）
- Mass Assignment（リクエストボディに内部フィールドを混入できる）
- 公開すべきでないファイルが公開 ACL でデプロイされる
- PII / 機密データがログ・レスポンスに漏れる
- ユーザーアップロードファイルがリポジトリにコミットされる

## Invocation

```
/sfad threat [feature]
/sfad threat docs/specs/{feature}/functional.md
/sfad threat --reverse @app/api/v1/orders.py   # 既存コードから抽出
```

## 入力

- `docs/specs/{feature}/functional.md`（/sfad spec の出力）
- 既存 PR / コードベースの認可パターン

## Execution Flow

### Step 1: アクター列挙

機能に関わる全アクターを列挙する。**最低でも以下 5 種類を必ず検討**:

| アクター | 例 |
|---|---|
| 未認証 | 公開エンドポイントを叩く誰か |
| 一般ユーザー（認証済み） | ログインしているが特権なし |
| リソース所有者 | そのデータを作った本人 |
| 同組織者 / チームメンバー | 所有者ではないが同じ組織 |
| **別組織 / 別テナント** | 正当な利用者だが、この機能のデータとは無関係な組織に属する |
| 管理者 / superuser | システム管理者 |
| 自動ジョブ / 内部システム | スケジューラ・cron・他サービス |

機能に該当しないアクターは「該当なし」と明記する。**列挙をスキップしてはいけない**。

### Step 2: 操作列挙

機能に含まれる全操作を列挙する。functional.md の API エンドポイントセクション、ジョブ、画面操作を全部拾う。

### Step 3: Authorization Matrix の作成

Step 1 × Step 2 の表を埋める。**全セルを必ず埋める**。空欄禁止。

```markdown
## Authorization Matrix

| 操作 | 未認証 | 一般ユーザー | リソース所有者 | 同組織者 | 管理者 | superuser |
|---|---|---|---|---|---|---|
| GET /resources（一覧） | ❌ 401 | ✅ | ✅ | ✅ | ✅ | ✅ |
| GET /resources/{id} | ❌ 401 | ✅ | ✅ | ✅ | ✅ | ✅ |
| POST /resources | ❌ 401 | ✅ | - 作成時点で所有者は未確定 | - 作成時点で組織紐付けは未確定 | ✅ | ✅ |
| PUT /resources/{id} | ❌ 401 | ❌ 403 | ✅ | ❌ 403 | ✅ | ✅ |
| DELETE /resources/{id} | ❌ 401 | ❌ 403 | ✅ | ❌ 403 | ✅ | ✅ |
| POST /admin/.../action | ❌ 401 | ❌ 403 | ❌ 403 | ❌ 403 | ❌ 403 | ✅ |

凡例:
  ✅       = 許可（200/201/204）
  ❌ 401  = 未認証拒否
  ❌ 403  = 認可拒否
  - {理由}  = 該当なし（操作の性質上発生しない）。**理由なしの裸の `-` は hook が deny する**
  ✅ (公開) = 意図的に未認証許可（理由を下に明記）
```

**ルール**:
- 全行・全列を埋める。空欄、および理由を伴わない `-` / `N/A` を残したら spec フェーズに戻る
  （どちらも「このセルを誰も検討していない」と区別がつかないため）
- 「✅ (公開)」と書いた項目は、**理由** を必ず下に明記する
- 「リソース所有者」と「同組織者」の挙動が同じなら、その判断根拠を明記する
- **「別組織 / 別テナント」列は単一テナントの案件でも省略しない**。「N/A: 単一テナント」と
  書けば通るが、書かずに済ませると `WHERE org_id` の抜けが仕様の時点で見えない
  （マルチテナントの越境は受託で最も多く、最も高くつく事故）
- 既存の類似 API があれば、その認可パターンと整合させる

### Step 4: IDOR / Mass Assignment チェック

各 mutation エンドポイントについて以下を確認:

```markdown
## IDOR / Mass Assignment チェック

### POST /resources

- **クライアントから受け取るフィールド**: name, description
- **サーバー側で設定するフィールド**: id, owner_id (= current_user.id), created_at, updated_at
- **クライアントから受け取ってはいけないフィールド**: id, owner_id, role, is_admin, organization_id（自動推論）
- **検証方法**: Pydantic schema で許可フィールドを明示し、それ以外を拒否

### PUT /resources/{id}

- **path の {id} と current_user の関係**: owner_id == current_user.id を必ず DB で確認
- **クライアントが id を改竄したら**: 404（存在しない場合）または 403（他人のリソース）
- **検証方法**: リソース取得時に owner_id を WHERE 句に含める or 取得後にチェック
```

### Step 5: Data Classification の作成

機能で扱うデータを分類する。

```markdown
## Data Classification

| データ | 分類 | 保存場所 | 配信方法 | 削除タイミング |
|---|---|---|---|---|
| ユーザーアバター | 個人情報 | S3 (private) | presigned URL | アカウント削除時 |
| アップロード画像 | 機密（本人特定可能） | S3 (private) | 認可付き endpoint | 90日後 |
| 操作ログ | 内部 | CloudWatch | 内部のみ | 30日 |
| ユーザー名 | 公開 | DB | API レスポンス | アカウント削除時 |

凡例:
  公開       = 誰でもアクセス可（意図的に公開）
  内部       = 開発・運用のみ
  個人情報   = PII。マスキング必須
  機密       = 個人を特定可能 or ビジネス機密
```

**ルール**:
- ファイルアップロードを扱う機能では必須
- 「公開」と書いた項目には **理由** を書く
- **`static/` 配下にユーザーアップロードを置く設計は禁止**（静的配信ディレクトリは認可なしで誰でも到達できるため。init.md の Day 0 チェックリストでも同項目を確認する）
- ログ出力時のマスキング規則を明記

### Step 5.5: 認可の失効

認可マトリクスは「**今の役割**」のスナップショットであり、役割が失われた後を問わない。
ログアウト・ロール剥奪・退会・契約終了の後もトークンやセッションが生き続ける事故は、
退職者アクセス・解約後アクセスとして受託で実際に請求問題になる。

```markdown
## 認可の失効

| 失効イベント | 発生源 | 反映までの許容時間 | 反映されるまでの挙動 | 検証 |
|---|---|---|---|---|
| ログアウト | 本人操作 | 即時 | - 即時失効のため猶予なし | AUTH-N |
| ロール剥奪（管理者→一般） | 管理者操作 | 5分（トークン有効期限） | 旧ロールで操作可能。監査ログに残す | AUTH-N |
| 退会 / アカウント無効化 | 本人 or 管理者 | 即時 | - 即時失効のため猶予なし | AUTH-N |
| 組織からの除名 | 管理者操作 | 即時 | - 即時失効のため猶予なし | AUTH-N |
| 契約終了 / プラン失効 | ジョブ | 24時間 | 読み取りのみ許可 | AUTH-N |
```

**ルール**:
- 全行を埋める。該当しないイベントは「N/A: 理由」（空欄と裸の `-` は hook が deny する）
- 「反映までの許容時間」が即時でないものは、**その間の挙動を仕様として書く**
  （書かなければ「たぶん大丈夫」で実装され、事故になったとき仕様に照らせない）
- 各行が Test List に AUTH-* を1件生成する

### Step 6: 横断的セキュリティチェック

```markdown
## 横断的セキュリティチェック

- [ ] CORS: 許可オリジンを明示している
- [ ] レートリミット: ログイン・認証系・重い処理に設定がある
- [ ] エラーメッセージ: システム内部情報（スタックトレース、SQL、内部 ID）が漏れない
- [ ] ログマスキング: PII を含むフィールド（email, phone, address）はマスク
- [ ] secrets: API キー・トークンは env / secrets manager 経由、ハードコード禁止
- [ ] 開発バイパス: テストヘッダー・フォールバック秘密鍵は本番でガード済み
- [ ] ファイルアップロード: サイズ制限・MIME バリデーション・ACL 設定済み
```

### Step 7: 出力の保存

`docs/specs/{feature}/threat.md` に保存する。
functional.md の Test List に **認可テスト** を自動追加する。
件数は固定ではなく**マトリクスから導出する** — 埋めた 36 セルが 5 件のテストにしか
ならないなら、空セル禁止という投資が検証に届いていないことになる。

**生成ルール**:

| マトリクスの内容 | 生成するテスト |
|---|---|
| ❌ セル1つ | AUTH-N を1件（その操作をその役割で叩くと宣言どおりの 401/403 が返る） |
| ✅ セル | 操作ごとに代表1件（全セル分は作らない — 通る経路は正常系 UC と重複するため） |
| 「✅ (公開)」セル | AUTH-N を1件（意図的な未認証許可が事故で塞がれていないことの確認） |
| リソース所有者の列を持つ操作 | IDOR-N を1件（他人の ID を指定して拒否される） |
| 書き込み操作（POST/PUT/PATCH） | MASS-N を1件（内部フィールド混入が無視される） |
| 別テナント列が ❌ の操作 | IDOR-N を1件（別組織の ID を指定して拒否される。所有者軸とは別に必要） |
| 管理者 / superuser が ✅ の書き込み操作 | AUDIT-N を1件（誰が・いつ・何に対して実行したかが記録に残る） |
| `- 理由` / `N/A: 理由` セル | 生成しない（発生しない操作なので検証対象がない） |

```markdown
- [ ] AUTH-1: 未認証で GET /resources を叩くと 401 が返る
- [ ] AUTH-2: 一般ユーザーで PUT /resources/{id} を叩くと 403 が返る
- [ ] AUTH-3: 同組織者で PUT /resources/{id} を叩くと 403 が返る
- [ ] IDOR-1: 他人のリソース ID を指定して PUT すると 403 が返る
- [ ] MASS-1: POST /resources に内部フィールドを混入しても無視される
```

これらは /sfad test で必ず実装される受け入れテストになる。

## Reverse Mode（既存コード対応）

```
/sfad threat --reverse @app/api/v1/orders.py
```

既存のエンドポイントから認可マトリクスを **逆引き** する。各 endpoint の `Depends(...)` を読んで現状の認可を表に起こし、**抜け** を赤字で示す。認可チェックが漏れたまま公開された「認可ゼロ」状態を早期に発見する用途。

## ゲート

- 全マトリクスのセルが埋まっていない → spec フェーズに戻る
- **❌ セルの数 > 生成した AUTH-* の数** → 停止。マトリクスに書いた拒否のうち
  検証されていないものが残っている（この差が空セル禁止の投資の回収率そのもの）。
  この判定は `/sfad drift` の **AUTHZ COVERAGE GAP** が CI でも機械的に再検査する
- 「別組織 / 別テナント」列が空欄のまま → spec フェーズに戻る
- 失効の表が未記入 → spec フェーズに戻る
- 「✅ (公開)」に理由が書かれていない → ユーザーに理由を要求
- IDOR / Mass Assignment チェックがスキップされた → エラー停止
- ファイルを扱うのに Data Classification が無い → エラー停止

このゲートを通らないと /sfad resilience に進めない。
