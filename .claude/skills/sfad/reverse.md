# SFAD Reverse — 既存コードからの仕様抽出

既存コードから振る舞いを読み取り、ユーザー承認を経て仕様書（`docs/specs/{feature}/functional.md`）を確定するスキル。
`/sfad spec` の逆方向: spec がユーザー要件→仕様化（新規）なのに対し、reverse は既存コード→仕様抽出→ユーザー承認（保守）。

## 設計思想

### 3つの情報源

```
コード     = 「今、何をしているか」（事実）
ユーザー   = 「何をすべきか」（意図）
仕様書     = 「何が正解か」（合意）← これを作る
```

### 出力の位置づけ

- 出力フォーマットは `/sfad spec` と**同一**（`docs/specs/{feature}/functional.md`）
- 以後は `/sfad test`、`/sfad impl`、`/sfad cycle` と共通パイプラインで処理可能
- reverse で仕様を確定した後の変更は `/sfad cycle` で仕様を更新する

## Invocation

```
# 方法 1: 機能名で指定（AI が関連ファイルを自動探索）
/sfad reverse "認証機能"
/sfad reverse --be "ユーザー管理"
/sfad reverse --fe "ダッシュボード"

# 方法 2: ファイル/パスで指定（具体的なコードを起点に探索）
/sfad reverse @app/api/v1/auth.py
/sfad reverse @src/app/dashboard/

# オプション
/sfad reverse --with-tests        # 仕様確定後にテストも自動生成
```

## Execution Flow

### Phase 1: 対象コードの特定と読み込み

**目的**: 仕様抽出の対象範囲を確定する。

#### 1-1. 入力の解釈

**機能名指定の場合**:
1. プロジェクト全体をスキャン（Glob + Grep）
2. 機能名に関連するキーワードでファイルを探索
3. ルーティング定義、コンポーネント export、モジュール名から該当ファイルを特定

**パス指定の場合**:
1. 指定ファイル/ディレクトリを起点にする
2. import/依存関係を辿って関連ファイルを収集

#### 1-2. 関連ファイルの自動探索

以下のカテゴリでファイルを収集:

| カテゴリ | 探索方法 | 例 |
|---------|---------|---|
| エントリポイント | ルーティング定義、export | `router.post("/login", ...)` |
| ビジネスロジック | import を辿る | `auth_service.py` |
| データアクセス | UseCase から辿る | `crud_user.py` |
| 型定義/スキーマ | import を辿る | `schemas/auth.py`, `types/auth.ts` |
| 既存テスト | テストディレクトリで対象名検索 | `tests/test_auth.py` |
| 設定/定数 | import を辿る | `config.py`, `constants.ts` |

#### 1-3. 対象範囲の提示

ユーザーに確認を求める:

```
対象コード分析:
  エントリポイント: app/api/v1/auth.py
  関連ファイル:
    - app/services/auth_service.py（ビジネスロジック）
    - app/crud/crud_user.py（データアクセス）
    - app/schemas/auth.py（リクエスト/レスポンス型）
  既存テスト: tests/test_auth.py（23テスト）

  この範囲で仕様を抽出しますか？
```

**ゲート**: ユーザーが範囲を承認するまで次に進まない。ユーザーはファイルの追加/除外を指示できる。

---

### Phase 2: 振る舞い抽出（AI によるコード分析）

**目的**: コードから「何をしているか」を体系的に読み取る。

#### 分析対象マトリクス

| 分析対象 | 抽出する情報 | コードの手がかり |
|---------|------------|----------------|
| エンドポイント/ページ | 機能の境界と API 契約 | ルーティング定義、コンポーネント export、デコレータ |
| 条件分岐 | ビジネスルール | if/switch/match、バリデーション、ガード節 |
| エラーハンドリング | 異常系パターン | try/catch、HTTPException、エラーレスポンス |
| 状態管理 | 状態遷移 | useState、Redux、DB ステータス更新、状態マシン |
| 型定義 | データ構造 | Pydantic model、TypeScript interface、struct、schema |
| 定数/設定値 | ビジネス制約 | マジックナンバー、設定値、閾値、enum |
| コメント/docstring | 開発者の意図 | 既存ドキュメント、TODO、FIXME |
| 既存テスト | テスト済みの振る舞い | test/describe/it のアサーション |

#### BE（API/サービス）の分析手順

1. **エンドポイント抽出**: ルーティング定義から HTTP メソッド、パス、認証要件を読み取る
2. **リクエスト/レスポンス**: スキーマ/型定義からデータ構造を読み取る
3. **ビジネスロジック**: UseCase 層の条件分岐をルールに変換する
4. **エラーパターン**: HTTPException、バリデーションエラーを列挙する
5. **データアクセス**: CRUD 操作からデータの永続化パターンを読み取る
6. **副作用**: メール送信、外部 API 呼び出し、イベント発行を検出する

#### FE（画面/コンポーネント）の分析手順

1. **コンポーネント構造**: export、props、イベントハンドラを読み取る
2. **状態管理**: useState/useReducer/Store の状態遷移を読み取る
3. **データフェッチ**: API 呼び出し、hooks、エラー/ローディング状態を検出する
4. **UI 分岐**: 条件レンダリング（三項演算子、&&、if）からルールを抽出する
5. **ユーザー操作**: onClick、onSubmit、onChange などのイベントハンドラを検出する
6. **バリデーション**: フォームバリデーション、入力制約を読み取る

### Phase 3: Example Map 生成（BDD 構造化）

**目的**: Phase 2 で抽出した振る舞いを `/sfad spec` と同じ Example Map 形式に構造化する。

#### 構造化ルール

- 1 つの主要な振る舞い = 1 Rule
- 各 Rule に最低 1 つの Example（コードから読み取れる具体例）
- コードから確認できない部分は Question として記録
- 各 Rule に**確信度**を付与

#### 確信度（Confidence Level）判定基準

| レベル | 条件 | 意味 |
|-------|------|------|
| **高** | コードとテストの両方で確認できる | ほぼ確実にこの振る舞いが正しい |
| **中** | コードにはあるがテストが不十分、またはコメントのみ | 振る舞いは読み取れるが意図は推測 |
| **低** | コードの意図が不明確、使われていない可能性、矛盾がある | ユーザー確認が必須 |

#### 出力フォーマット

```markdown
## Example Map: {機能名}（コードから抽出）

### Story
{コードから推測したユーザーストーリー}

### Rules & Examples

**Rule 1: {ルール}** [確信度: 高]
- Example: {具体例1 — コードから読み取った値}
- Example: {具体例2}

**Rule 2: {ルール}** [確信度: 中]
- Example: {具体例1}

**Rule 3: [不明] {推測されるルール}** [確信度: 低]
- Example: {コードにはあるが意図不明}

### Questions（AI が検出した不明点）
- {コードから答えが読み取れなかった疑問}
```

---

### Phase 4: 不明点・矛盾の検出

**目的**: 仕様として確定する前に、コードの問題点を洗い出す。

#### 問題カテゴリ

| カテゴリ | タグ | 内容 | 検出方法 |
|---------|------|------|---------|
| **Dead Code** | `[DEAD CODE]` | 到達不能なコードパス | 呼び出し元がない関数、到達不能な else ブランチ |
| **Undocumented Behavior** | `[UNDOCUMENTED]` | テストもコメントもない振る舞い | テストカバレッジのギャップ、マジックナンバー |
| **Inconsistency** | `[INCONSISTENT]` | コードとテストの矛盾 | テストの期待値とコードの実装値の不一致 |
| **Missing Edge Case** | `[MISSING]` | 未処理の境界条件 | null チェック不足、0件/空文字/最大値の未処理 |
| **Security Concern** | `[SECURITY]` | セキュリティ上の懸念 | 入力サニタイズ不足、認証チェック漏れ、機密情報露出 |
| **Implicit Rule** | `[IMPLICIT]` | 暗黙の業務ルール | コメントなしの条件分岐、ハードコード値 |
| **N+1 Query** | `[N+1 QUERY]` | ループ内の個別 DB アクセス | for ループ内の select/get、lazy loading の連鎖 |
| **Missing Index** | `[MISSING INDEX]` | WHERE/JOIN 対象にインデックスなし | フルスキャンが発生するクエリ、複合条件のインデックス不足 |
| **Session Hold** | `[SESSION HOLD]` | 外部 API 呼び出し中の DB セッション保持 | セッションスコープ内での HTTP/外部通知 API 呼び出し、asyncio.sleep |

#### 検出結果の出力

```
検出された問題:
  [DEAD CODE]     auth.py:245 — リフレッシュトークン無効化ロジック（呼び出し元なし）
  [IMPLICIT]      auth.py:128 — ロック回数 5 回（なぜ 5 回？）
  [MISSING]       — アカウントロック解除の手段がない
  [SECURITY]      auth.py:89 — パスワードリセットのレート制限なし
  [UNDOCUMENTED]  auth_service.py:67 — OTP 有効期限 300 秒（テストなし）
  [INCONSISTENT]  test_auth.py:45 vs auth.py:92 — ロック閾値が異なる
  [N+1 QUERY]     service.py:120 — for ループ内で個別に select(Role) を発行
  [MISSING INDEX] — user_id + organization_id の複合インデックスなし（フルスキャン）
  [SESSION HOLD]  jobs.py:450 — 外部通知 API 呼び出し中に DB セッションを保持（プール枯渇リスク）
```

---

### Phase 5: ユーザーバリデーション（最重要ゲート）

**目的**: AI が抽出した仕様をユーザーが「これが正解」と承認する。

#### 提示フォーマット

```
仕様抽出結果: {機能名}

Example Map:
  Story: {ストーリー}
  Rules: {N}（確信度: 高×{n}, 中×{n}, 低×{n}）
  Examples: {N}
  Questions: {N}

検出された問題:
  {Phase 4 の検出結果}

以下を回答してください:
1. Rule 1〜{N} は正しい仕様ですか？修正はありますか？
2. Questions への回答
3. 検出された問題への対応方針
```

**ゲート**: ユーザーが全ての Rule を承認し、全ての Question に回答するまで次に進まない。

#### ユーザーの回答パターンと対応

| 回答 | AI の対応 |
|------|----------|
| 「Rule X は正しい」 | 確信度を「高」に上げ、仕様として確定 |
| 「Rule X は間違い。正しくは Y」 | 仕様を修正（バグとして記録） |
| 「Rule X は使っていない。削除」 | Dead Code として技術的負債に記録 |
| 「Question に対する回答」 | 新しい Rule または既存 Rule の修正に反映 |
| 「問題 X は修正すべき」 | 技術的負債リストに追加 |
| 「問題 X は仕様通り」 | 仕様として確定、コメントに理由を記録 |

---

### Phase 6: 仕様ファイル生成

**目的**: ユーザーの承認を反映し、`/sfad spec` と同一フォーマットで仕様書を出力する。

#### 出力先

```
docs/specs/{feature}/functional.md
```

#### テンプレート

reverse も `/sfad spec` と同じ functional.md テンプレートを使う（二重管理を避けるため、ここには転記しない）。

- FE: `references/spec-template-fe.md`
- BE: `references/spec-template-be.md`

frontmatter の `spec_confirmed_at` には **Phase 5 でユーザーが仕様を承認した時点のコミット SHA** を記入する
（`/sfad spec` では仕様確定時点、reverse では抽出承認時点という違いのみで、書き込むタイミングの意味は同じ）。

#### reverse 固有の追加セクション

共有テンプレートに対し、reverse は以下の 2 セクションを追加する。

**概要の直後に挿入するメタデータ**:

```markdown
## メタデータ
- **生成方法**: /sfad reverse（既存コードからの抽出）
- **対象コード**: {エントリポイント} + 関連{N}ファイル
- **抽出日**: {YYYY-MM-DD}
- **確信度**: 高×{n}, 中×{n}（平均: {高|中}）
- **検出問題**: {カテゴリ別カウント}
```

**受け入れ基準の後に追加するセクション**:

```markdown
## 既知の技術的負債
- [ ] {[タグ] 問題の説明}
```

### Phase 7: テスト生成（オプション）

**目的**: 確定した仕様に基づいてテストを生成し、現在の振る舞いを固定する。

**起動条件**: `--with-tests` フラグ指定時、または `/sfad cycle` から呼ばれた場合。

#### 7-1. 既存テストのギャップ分析

既存テストがある場合:
1. 既存テストのアサーションと仕様の Test List を照合する
2. 仕様をカバーしているテスト / カバーしていないテストを分類する
3. 不足テストのみ追加生成する

既存テストがない場合:
1. Test List 全体からテストを生成する（`/sfad test` と同じフォーマット）

#### 7-2. テスト生成

`/sfad test` と同じフォーマット・ルールでテストを生成する。
ただし reverse 固有の注意点:

- **テストは「現状を正として固定する」ためのもの**
- 現状のコードに対して**全 Green であるべき**
- もし Red になるテストがあれば、それは仕様とコードの不一致 → ユーザーに報告

#### 7-3. テスト実行と検証

```
テスト生成結果:
  既存テスト: {N} テスト（{テストファイルパス}）
  仕様カバレッジ: {既存}/{全体}（{%}）
  追加生成: {N} テスト（不足分）

  全テスト実行: {N}/{N} Green
  → 現在の振る舞いが仕様として固定されました
```

**Red テストがある場合**:
```
テスト結果に不一致があります:
  {テスト名}: Expected {X} but got {Y}

これは以下のいずれかです:
  (a) コードにバグがある → 修正が必要
  (b) 仕様が間違っている → Phase 5 に戻って修正

どちらですか？
```

## ゲートとユーザー介入ポイント

| Phase | ゲート | 説明 |
|-------|--------|------|
| Phase 1 | 範囲承認 | 対象ファイルの範囲確認。追加/除外を受け付ける |
| Phase 2 | なし（自動） | AI がコードを分析 |
| Phase 3 | なし（自動） | AI が Example Map を構造化 |
| Phase 4 | なし（自動） | AI が問題を検出 |
| Phase 5 | **仕様承認** | 全 Rule の承認 + 全 Question への回答。最重要ゲート |
| Phase 6 | なし（自動） | 仕様ファイル生成 |
| Phase 7 | Red テスト時 | テストが Red の場合、バグか仕様誤りかの判断を求める |

## エラー時の振る舞い

- **関連ファイルが見つからない**: 探索範囲を広げて再試行。それでも見つからなければユーザーに手動指定を依頼
- **コードの意図が読み取れない**: 確信度「低」で記録し、Phase 5 でユーザーに確認
- **既存テストが壊れている**: テスト結果をそのまま報告し、バグか仕様変更かをユーザーに判断を求める
- **仕様とコードの矛盾**: Phase 5 でユーザーに報告し、どちらが正しいか確認

## 他コマンドとの関係

```
/sfad reverse = Phase 1-7（既存コード → 仕様書）

reverse 完了後:
  /sfad cycle [feature変更]  = 仕様更新 + テスト修正 + 実装修正
  /sfad test                 = 追加テスト生成
  /sfad impl                 = 実装変更

手動で部分実行:
  /sfad reverse             = Phase 1-6（仕様抽出のみ）
  /sfad reverse --with-tests = Phase 1-7（仕様抽出 + テスト生成）
```
