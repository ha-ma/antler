# SFAD Impl — Double-Loop テスト駆動実装

Red テストを Green にする実装を回すスキル。Double-Loop の構造は SKILL.md の図が正。

## Invocation

```
/sfad impl                              # 全 Red テストを Green にする
/sfad impl @path/to/test-file           # 特定テストファイル
/sfad impl --refactor                   # Green 後のリファクタリング
/sfad impl --regression "バグの説明"     # 回帰テスト TDD サイクル
```

## Step 1: Red テストの分析

1. テストファイルを読み、実行して Red を確認
2. 仕様（`docs/specs/{feature}/functional.md`）の Test List と照合
3. 各テストから要件を読み取る: モック宣言 → 依存モジュール / アサーション → 必要な出力 / テストデータ → 型

## Step 2: 実装計画

テストから逆算して必要なファイルと順序を決める。

**配置・命名・レイヤ規約・Outside-In の具体的な順序はスタック層が正**:
そのプロジェクトのスタック（stacks/{stack} 由来の rules / skills / hooks）に従う。
編集するファイルの層のルールは自動ロードされ、違反は hook が write-time に deny する。
SFAD 側の原則は1つだけ — **外側（ユーザー/クライアント境界）から内側へ**。
外側を先に書く過程で内側のインターフェースが発見される（GOOS の Interface Discovery）。
これは**テストを書く順序**であって、plan.md の PR 表の並び（マージ順＝依存順）とは別物。

## Step 3: Canon TDD サイクル（Test List の各項目で繰り返す）

```
For each item in Test List:
  1. [Red]      テストが失敗することを確認（失敗テストなしにプロダクションコードを書かない）
  2. [Green]    テストを通す最小コードを書く（YAGNI: アサーションを満たすだけ）
  3. [Refactor] Green のまま改善。Red になったら戻す
  4. [Test List 更新] 実装中に発見した新シナリオを [ADDED] で追記し、テストを書いてから次へ
  5. [Next]     次の項目へ
```

## Step 4: 実装ルール

1. **テストのアサーションだけを満たす**（YAGNI）
2. **既存パターンに従う**: プロジェクト内の類似コードとスタック規約を参照
3. **スタック固有の禁止事項はスタック層に委譲**: セキュリティ（Mass Assignment・認可・
   シークレット）、レイヤ境界、フレームワーク作法は、各スタックの rules/hooks/CI が
   機械的に強制する。lint が捕捉する規則もここに書かない（lint で強制済み）
4. **エラー詳細の非露出**: 内部例外・スタックトレースをユーザー応答に含めない
5. **構造化ログ**: print/console.log のデバッグ出力を残さない

## Step 5: Green 確認

UC テスト → 対象 Green / 受け入れテスト → まだ Red（残 UC があるため）が正常。
全 UC + 全 S が Green になった時点で受け入れテストも Green になる。

## Step 6: エッジケース検出（全 Green 後）

カバレッジギャップを列挙してユーザーに提示:

```
[EDGE] 境界値: {パラメータ}が負の値の場合が未定義
[EDGE] null: {フィールド}が null の場合のテストなし
[EDGE] 並行: 同時リクエスト時の挙動未検証（決定的に再現できる場合のみテスト化）
追加テストを生成しますか？
```

承認されたものだけ Red → Green で追加し、Test List に [EDGE] で追記。

## Step 7: 最終リファクタリング

**テストは Green のまま**行う。以下の観点を上から順に当て、**当たったものだけ**直す。
全部に何か書こうとしないこと（無理な指摘は無指摘と同じ）。

配置・命名・レイヤ規約はスタック層が正だが、**ここに挙げるのは言語に依存しない設計の観点**
なので SFAD 側が持つ。6スタックに同じリストを複製すると必ず乖離するため、置き場所はここ1つ。

| 観点 | 何を見るか | 直し方 |
|---|---|---|
| **重複** | 同じロジックの形が2箇所以上に現れた | 共通の形を抽出し、両方から呼ぶ |
| **投機的な汎用化** | 仕様が要求していない引数・分岐・抽象が入った | 消す。実際の必要が出るまでインライン化しておく |
| **浅い委譲** | ほぼ素通しするだけの関数・クラスができた | 消して呼び出し先を直接呼ぶ |
| **散弾銃的変更** | 1つの論理的変更のために複数ファイルを触った | 一緒に変わるものを1箇所に集める |
| **発散的変更** | 1つのモジュールを無関係な複数の理由で触った | 変更理由ごとに分ける |
| **基本型への執着** | ドメイン概念が文字列や数値のまま流れている | その概念に小さな型を与える |
| **命名** | 何をするか・何を保持するかが名前から読めない | 改名する。正直な名前が出てこないなら設計が曖昧 |

**削除テスト**: 迷ったらそのモジュールを消したと想像する。複雑さが消えるなら素通しだった。
複雑さが呼び出し側 N 箇所に現れるなら、それは働いている。

**AI が書いたコードで実際に起きるのは上から2つ**（重複と投機的な汎用化）。
テストが Green だと通ってしまい、lint も型チェックも捕まえない。ここが最後の砦。

## Step 8: 静的解析ゲート（完了の必須条件）

プロジェクト既存の設定で実行し、**エラー 0 件になるまで完了としない**:

1. リンター（新規・変更ファイルのみ。`--fix` 活用）
2. フォーマッター（差分なし）
3. 型チェック（設定がある場合）
4. 依存方向チェック（スタックにある場合: import-linter / deptrac / ESLint boundaries）

## Bug-Fix TDD（回帰テスト）

```
/sfad impl --regression "バグの説明"
```

1. バグを再現する失敗テストを1つ生成（Red）→ 2. Red 確認 → 3. 修正（Green）→ 4. Refactor

**鉄則: バグ修正にテストなし = 再発保証なし**

## Test List の管理

Test List（functional.md 内）は実装中に育つ。完了時は全項目にチェックが付いている:

```
- [x] UC-1: ページタイトル表示
- [x] UC-2: 日付フォーマット表示 [ADDED]   ← 実装中に発見
- [x] EDGE: skip が負でもクラッシュしない [EDGE] ← エッジケース検出で追加
```

## Output

```
実装完了 — Double-Loop 全 Green
  外側: 受け入れテスト ✅ / 内側: UC ×{N} + S ×{N} + EDGE ×{N}
  Test List: {初期}+{追加} = {計}/{計}
  静的解析: lint ✅ format ✅ 型 ✅ 依存方向 ✅
次: /sfad cycle {次の機能} または git commit
```
