### 追加すべき Example（既存 Rule の穴）

- **[重要度 1][R9・R11] 所有者でない端末の挑戦が、跡を残さずに終わる** — 理由: R9 と R11 が噛み合っていません
  - 問題: R9 の「アラート OFF で挑戦」には所有者の条件がありません。一方 R11 と resilience.md では、所有者でない端末の運転は黙って保存されません。運転の前に「記録に残らない」と分かる Rule も、運転の後にその人の結果を見せる Rule もありません。
  - 起きる具体例:
    - (a) SNS の共有リンクから SSR、「EZO ROAD で開く」、A-7 と進んだ閲覧者が、OFF で挑戦して完走します。運転の終了は `/t/:id` に戻るので、見えるのは所有者の「D2 まで走った。」です。閲覧者からは自分の完走が消えたように見えます。
    - (b) 所有者が LINE で自分に送ったリンクを、LINE のアプリ内ブラウザで開きます。localStorage が別なので、本人なのに保存も削除もできません。案内は「削除は、この旅をつくった端末からできます」だけで、なぜできないかが分かりません。
  - 提案（推奨案）:
    - R9 に「トークンの無い端末では、挑戦のリンクに『この端末の運転は記録に残りません』を添える（隠さない）」を足す。
    - R11 に「`not-owner` を受けた呼び出し側は `recordHref` へ移らず、その運転の結果をその場で見せて『自分の旅をつくる』へ誘う」を、drive-link への契約として書く。
    - Example を 2 つ足す。「共有リンクの閲覧者が挑戦して完走しても、所有者の記録は変わらず、本人の画面に結果が出る」と「所有者が別のブラウザで開くと、削除の代わりに理由の案内が出る」。

- **[重要度 2][R3] 「日ごとの最新」と OFF 挑戦・やり直し・日の順番がぶつかる** — 理由: R3 の否定形（最新が悪い結果のとき、日の順が逆のとき）に Example がありません
  - 問題: OFF 挑戦（A7-4、SHOULD の遊び）の結果が、本番の記録（ON の完走）と同じ列で上書きし合います。状態の見出し「D{n} まで走った。」の n も定義がありません（R3 にあるのは保存順で決める「最後に走った日」だけです）。
  - 起きる具体例:
    - (a) 全日を ON で完走して「守りきった。」になった人が、D3 を OFF で挑戦して衝突します。D3 が collided になり、旅は partial、守れた楽しみも減ります。挑戦を勧めた画面が、本人の記録を壊します。
    - (b) D1 ✓・D2 ✓・D3 ✕ のあと、D1 を挑戦し直します。挑戦のリンクの日も n も 1 になり、「D1 まで走った。」と出ます（D3 まで行ったのに）。
    - (c) `plan.days[].stops` には日をまたいだ一意の制約がありません。同じ楽しみが 2 日に入っていると、分子と分母に 2 回数えられます。
    - (d) やり直しと挑戦を繰り返して 100 件に達すると、そのあとの完走はすべて 409 になり、記録が古いまま固まります。
  - 提案（推奨案）:
    - 日の結果は「`alertEnabled=true` の最新の run」で決め、ON の run が無い日だけ OFF の最新を使う。
    - OFF 挑戦の結果は、しおりの行に「OFF ✓ / ✕」として別に出す。
    - n は「run のある日の最大」とする。挑戦の日はそのまま「最後に走った日」でよい。
    - 楽しみは id で一意にして数える。
    - 100 件は「日ごとの最新を消さない範囲で古い run から消す」か、上限を 1 日あたりにする。どちらも Example を付ける。

- **[重要度 3][R10] 削除の連鎖が「今ある表」に閉じていて、確認の文言が threat.md と違う** — 理由: 外部キーを張らない設計（plan.md）なので、漏れを止めるものが他にありません
  - 問題:
    - (a) threat.md は確認に「共有先に表示されたカードは残ることがあります」を入れると書いています。R10 の確認文（「削除すると、この記録の URL は誰も開けなくなります。元に戻せません」）にはそれがありません。
    - (b) stop-events の表は Deferred で「後からマージする側が足す」とされていますが、足し忘れを検出する仕組みがありません。
    - (c) A5-5 で sim から送る Capture は、旅の id を持ちません（`packages/schema/src/capture.ts`）。旅を消しても、同意して送った画像は残ります。そのことがどこにも書かれていません。
  - 起きる具体例: stop-events が先にマージされ、record が後からマージされます。どちらも相手の表を消さずに CI を通ります。旅を削除しても `trip_events` の行（立ち寄り先や時刻）が残り、「記録の URL は誰も開けなくなります」とは別に、中身が DB に残り続けます。
  - 提案（推奨案）:
    - UC-5a に「`sqlite_master` を列挙し、`trip_id` の列を持つすべての表について、削除後にその旅の行が 0 件であることを確かめる」テストを足す。表が増えれば自動で落ちる。
    - R10 の確認文に「共有先に表示されたカードは残ることがあります」と、Capture 導入後は「送った鹿の画像は残ります（旅とは結びついていません）」を足す。4 言語で。
    - あとで OG の画像をメモリに持つ（[重要度 5]）なら、削除でそれも捨てることを R10 の「消すもの」に足す。

### 追加すべき Question（未定義の振る舞い）

- **[重要度 6] OG・SSR の描画で、上限と基準が決まっていないもの** — 誰の知識が必要か: [Dev / PO]
  - 問題: 次の入力に範囲・扱いが決まっていません。
    - `title` は最大 200 字（`trip-plan.ts`）。
    - `plan.days` は `.min(1)` だけで上限がない。
    - XML エスケープでは消えない制御文字（U+0000〜U+001F）。
    - POST runs の body の大きさ（POST /api/trips には 16 KB の `bodyLimit` があります）。
  - 起きる具体例:
    - (a) 200 字のタイトルや 10 日以上の旅で、1200×630 からはみ出します。
    - (b) Claude の文に制御文字が混じると resvg が例外を投げ、500 になり、共有カードが画像なしになります。
    - (c) `zod` の検証の前に、何 MB もの JSON を読まされます。
    - (d) 【ドメイン規範: 日付とタイムゾーン】eyebrow の「出発日 – 返却日」とログの時刻を、サーバーの TZ（UTC のことが多い）で書くと、日付が 1 日ずれます（例: 11/10 00:30 JST が 11/09 になる）。
  - 提案（推奨案）:
    - タイトルは 2 行で切って末尾を「…」に、日の行は 7 行までで、それ以上は「ほか n 日」にする。
    - SVG に入れる前に制御文字を取り除く。
    - POST runs に `bodyLimit` 16 KB（超えたら 413）を付ける。
    - 日付と時刻は `Asia/Tokyo` を明示して書く（R5・R6・R7 に 1 行）。
    - それぞれ UC-6・UC-7・UC-1 に Example を足す。

- **[重要度 4] 共有 URL・og:url・og:image の出どころをどれにするか** — 誰の知識が必要か: [Dev]
  - 問題: R1 は「共有の URL は `PUBLIC_API_URL`、無ければ要求の origin」としています。UC-9a は「`VITE_API_BASE_URL` + `/t/{id}`」です。出どころが 2 つあり、要求の origin への後退は、プロキシの後ろでは内部の http を指します（`TRUST_PROXY` のある構成）。
  - 起きる具体例:
    - (a) 本番で `PUBLIC_API_URL` を入れ忘れると、og:image が `http://127.0.0.1:8787/t/…/og.png` になり、どの SNS でもカードの画像が出ません。テストは app.request で通ってしまいます。
    - (b) `VITE_API_BASE_URL` が相対パス（`/`）や開発用の値だと、コピーしたリンクが他人の端末で開けません。
    - (c) `Host` ヘッダを書き換えた要求に、偽の og:url を返します（今は `no-store` なので害は限られますが、前に CDN を置くと汚染されます）。
  - 提案（推奨案）: 本番（`NODE_ENV=production`）では `PUBLIC_API_URL` と `SIM_PUBLIC_URL` を必須にし、無ければ起動で止める（env の zod）。要求の origin への後退は開発だけにする。sim の共有 URL は `VITE_PUBLIC_API_URL` の 1 つにまとめて R1 に書く。UC-7a に「`Host: evil.example` でも og:url は `PUBLIC_API_URL`」を足す。

### 甘い仮定（明文化が必要）

- **[重要度 5] 「同時 2 枚、超えたら 503」で OG の濫用を抑えられる** → **毎回描くこと自体が攻撃面になる、と明文化する**
  - 問題: `no-store` で毎回描き、枠は 2 つ、3 枚目は待たずに 503 です。CJK フォントを使った 1 枚の描画は数百 ms かかります。
  - 起きる具体例:
    - (a) 1 つの IP から 2 本を並列で投げ続けるだけで（20 件／分の範囲内に収まります）、枠がふさがり、SNS のクローラーには 503 しか返りません。シェアのカードが全員ぶん画像なしになります。
    - (b) クローラーは多くの利用者で IP を共有しています。同じ時間帯にいくつかシェアされると、クローラー側の IP が 20 件／分に当たって 429 になります。
    - (c) システムのフォントの読み込みを描画ごとにやると、1 枚あたりの時間がさらに延びます。
  - 提案（推奨案）:
    - 描いた PNG をプロセスのメモリに LRU で持つ（キーは（旅の id, 最後の seq）、例えば 200 件）。run の保存と削除で捨てる。HTTP の `no-store` は残すので、削除の即時性は変わらない。
    - フォントの DB は起動時に 1 回だけ読む。
    - 描画に時間の上限（例: 3 秒）を付ける。
    - キャッシュに当たった応答は同時 2 枚の枠を使わない。
    - UC-6 に「同じ id の 2 回目は描かない」「run の保存のあとは描き直す」「削除のあとは 404」を足す。

- **[重要度 7] 「記録は個人を特定しないので、丸ごと見せてよい」** → **公開するのは画面に出す分だけ、と明文化する**
  - 問題: R4 の `GET /api/trips/:id/record` は plan を丸ごと返します（1 人あたりの予算・泊まる町・seed・出発時刻）。IDOR-2 が禁じているのはハッシュと runId だけです。brief-map では「ID を知る人」は旅の仲間でしたが、record は SNS で不特定多数に広げるための URL です。
  - 起きる具体例: 旅の前に「この旅をつくった」とシェアすると、URL を見た誰でも、出発日・返却日・人数・泊まる町を JSON で取れます。投稿者のアカウントと結びつけば、家を空ける期間が公になります。
  - 提案（推奨案）: record の JSON と SSR は、画面に出す欄だけに絞った形（タイトル・日程・各日の楽しみ・人数）を `TripRecordSchema` で返し、予算・泊まる町・seed を外す。sim の A-7 が全体を要るなら brief-map の API を使う。IDOR-2 に「予算・seed が応答に無い」を足す。日程を出すかどうかは PO の判断として Question に回してもよい。

### 問題なし

所有者トークンの照合（長さが変わらない比較、401 と 403 の分け方）、知らない欄を 400 にする strict の検証、冪等な再送、削除と保存の同時実行を同じトランザクションで直列にすること、SSR の CSP（`default-src 'none'`・`frame-ancestors 'none'`）と noindex は、筋が通っています。
