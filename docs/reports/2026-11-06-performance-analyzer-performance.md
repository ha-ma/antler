## 結論

Critical なし。毎フレームの負担（R1）、表示しないときの `?fps=1`（R2）、先読みの重複（R5）、バンドルの検査（R6）に確定した問題は無い。
主な指摘は 3 つ。

1. **R4 の DPR の段は 30 fps に張り付く端末を「遅い端末」と見て下げる**（W1）。R1 は 30 fps への張り付きを正常として扱う設計なので、仕様の中で食い違う。ch6 のスマホ目標が 30 fps なので、狙った端末で起きる。
2. **計測スクリプトに、R4 が計測を書き換える穴と、判定から漏れる区間がある**（W2・W3）。`danger` と `settle` は表に出すだけで判定しない。
3. **A-2 の先読みは `import()` なので、取得だけでなく three・R3F の評価（parse と実行）も A-2 の最中に走る**（W4）。Slow 4G では帯域も地図と取り合う。A-2 を測った数字がまだ無い。

前の申し送りの W1〜W3 を「直さない」とした判断は、PC・スマホ相当の CPU については無理がない（下の節）。W2 だけは M2 の GPU の測定が弱い GPU の証拠にならない。

## Warning（改善推奨）

### W1. DPR を下げる段が、30 fps に張り付く端末と、読み込み直後の窓で誤って下がりうる

- 場所: `domain/quality.ts:11-13`（`LOW_FPS = 45`、`LOW_WINDOWS = 2`）、`scene/AdaptiveDpr.tsx`
- 事実:
  - 判定は「2 秒の窓の平均 fps が 45 未満」が 2 窓続くこと。窓の平均は端末の更新レートを見ない
  - iOS の低電力モードや省電力の Android は rAF を 30 Hz に張り付ける。R1 はこの端末を「33.3 ms の揺れを数えない」と正常に扱っている（`DROPPED_FRAME_MS = 40` の根拠）。ところが R4 では 30 fps < 45 なので、**起動から約 4 秒で 1.5 → 1.25、さらに 4 秒で 1** まで必ず下がる。仕事に余裕があっても下がる。DPR を下げても 30 Hz の上限は変わらないので、利益が無いまま輪郭だけ粗くなる
  - 同じ理由で、**30 fps が目標のスマホが 32〜44 fps で走る場合も下がる**。合格の fps 30 と 45 の線が一致していない。逆に PC が 46〜58 fps で走っても下がらない（R3 の PC の合格は中央値 59 以上）。線の置き方は意図的でもよいが、仕様に「45」の根拠が無い
  - 窓の最初の 2 秒は Canvas の最初の描画（シェーダのコンパイル、ミラーの最初の描画。前のレポート I3）を含む。スマホで 0.8 秒止まると 1 窓目だけで約 37 fps になる。2 窓続く条件があるので 1 回では下がらないが、2 窓目も出発前後のチャンク作りと重なると誤って下がる余地がある（`MAX_FRAME_MS = 1000` 未満の止まりは数える）
  - タブを隠して 1 秒未満で戻った場合の 1 フレーム（0.6〜0.9 秒）も窓に入る。単発では下がらないが、窓の境をまたぐ素早い切り替えを 2 回で下がる
  - 戻らないので、一度の誤判定が走行の終わりまで残る。さらに `AdaptiveDpr` は画面を出るたびに `INITIAL_QUALITY` から始まるので、**A-2 → 運転 → A-6 → もう一度**のたびに遅い端末は 4〜8 秒を 1.5 の重い状態で過ごす
  - 端末の DPR が 1.25 のとき（Windows の 125%）は段 1 が見た目に何も変えず、実質 4 秒余計に待つ。DPR が 1 の端末は 3 段とも変化なし（無害）
- 影響: 目標のスマホで DPR が不要に 1 まで落ちる（画質の低下）。遅い端末の再入場の 4〜8 秒（体感のカクつき）
- 改善（小さい順）:
  1. 窓の fps を、その端末の「張り付き」と比べる。窓の中央値の間隔が 31〜36 ms で、ばらつき（p95 − p50）が 3 ms 未満なら張り付きとみなし、遅い窓に数えない。または、最初の数窓で観測した最速の fps を基準にして、その 75% 未満を遅いとする
  2. 最初の窓（Canvas の最初の 2 秒）は捨てる。`document.visibilitychange` で窓を空にして、戻った 1 フレームを捨てる
  3. 下げた段を `sessionStorage`（または module の変数）に残して、次の入場の初期値にする。同じ値に変わらない段（`dprOf` が前と同じ）は飛ばす
  4. 判定の線の根拠（45）を仕様 R4 に 1 行書く
- 推定効果: 低電力モードの端末での不要な画質低下をなくす。遅い端末の再入場で 4〜8 秒の重い状態がなくなる
- 計測方法: `measure-drive.mjs` に `--fps-cap 30`（CDP で rAF を 30 Hz に落とす手段が無いので、`page.addInitScript` で rAF を 2 回に 1 回間引く）の 1 構成を足し、DPR が 1 まで落ちないことを確かめる。A-7 の `frames` と合わせて見る

### W2. 計測スクリプトの中で R4 が計測の条件を書き換える

- 場所: `scripts/perf/measure-drive.mjs:213-229`（Canvas の大きさは**最後に 1 回**読む）、`judge()`（`Canvas が … のはず` の理由）
- 事実: phone の構成（CPU 4× 減速）は 60 fps に届かない場面が出うる。45 fps 未満が 4 秒続くと DPR が 1.5 → 1.25 → 1 に下がり、同じ行の前半と後半で画素数が違う。見えるのは最後の Canvas の大きさの不一致だけで、「その行は無効」と判定されるが原因が DPR の自動降下だとは出ない。逆に、降下がなければ有効な行に「R4 が効いていたか」が書かれない
- 影響: 合格・不合格の行が R4 の動作と混ざる。R4 を入れる前後の比較ができない。降下の時刻も分からない
- 改善: `?adaptive=0`（計測だけ AdaptiveDpr を無効にするクエリ。`?fps=1` と同じ作り）か、DPR を 1.5 に固定する引数を足す。もしくは、降下した段を 300 ms の問い合わせの中で Canvas の `width` から読んで、行の `dprSteps: [{ at, canvas }]` に残す。R3 の合格は固定の状態で見て、R4 の動作は別の行で見るのが読みやすい
- 推定効果: 数字の読み間違いを避ける（計測の信頼性）

### W3. 判定から漏れている区間と、実際の条件との違い

- 場所: `measure-drive.mjs:104-120`（`MIN_FRAMES`・`judge`）、タグ `settle`・`danger`
- 事実:
  - **`danger`**（赤が出て 1 秒後以降。画面全面が赤＋ shadow-danger の発光＋鹿のピクト）は表に出すだけで `judge` に入っていない。この feature で最も大事な描画の状態なのに、最大・p95 の合格が無い。`onset` の 1 秒だけが判定される
  - **`settle`**（出発・やり直しの 2 秒）は判定から除かれている。R1 は「出発・やり直しの直後の区間の作り直しも利用者に見える引っかかりなので数える」と決めているのに、計測は逆に除く。出発直後は音の初期化・最初の区間の構築・ミラーの初回で最も重い 1 フレームが出やすい。1 秒描いてから出発する手順（ウォームアップ）で、いちばん重い部分を隠している
  - 方法の違い: 計測は `approach` を 4× で走る。要件の利用者は 1× 〜 4× を選ぶので、それ自体はより厳しい側で問題ない。ただし `approach` の 4× は物理のサブステップ数や降るものの `advance`（前のレポート I5）も 4 倍になり、描画の仕事とは別の負荷が混ざる。`zone`（1×）の p95 と比べて、どちらが重いかを報告に残すと切り分けられる
  - ヘッドレスの Chromium は、実際のウィンドウへの合成（macOS のウィンドウサーバ、ProMotion の 120 Hz）を含まない。vsync あり行の「60 fps に張り付く」は、ウィンドウ表示のコストを含まない
  - 1 場面 75 秒は、長い走行（1 日の行程）の主要な GC（V8 の major GC）や、ヒープの増え方を見るには短い。道路の区間は `number[]` を 1 区間あたり約 2.7 万回 push して作る（前のレポート W1）ので、モバイルの major GC 候補になる
- 改善:
  1. `danger` を `approach` と同じ基準で判定に入れる（`MIN_FRAMES.danger = 120` 程度。鹿が出る場面を毎回走らせる設計なら足りる）。足りない場面は無効の理由に出す
  2. `settle` は判定の基準を別に置く（PC: 最大 50 ms、phone: 最大 100 ms。ここは緩くてよい）。「除外」から「別の基準で判定」に変える
  3. 1 構成だけ headed（`headless: false`）で PC の 1 場面を走り、ヘッドレスとの差を報告に 1 行残す
  4. 5 分の走行を 1 場面だけ走り、`dropped / counted` と `performance.memory.usedJSHeapSize`（Chromium のみ）を 30 秒ごとに残す
- 推定効果: 判定の抜け（赤の状態の最大フレーム、出発直後のヒッチ）を埋める

### W4. A-2 の先読みは評価（parse・実行）まで A-2 の最中に走り、地図と帯域も取り合う

- 場所: `app/preload-drive.ts:14-24`、`app/routes.tsx:23-28`（`schedulePreloadDrive` を A-2 のチャンクを読んだ直後に予約）
- 事実:
  - 先読みは `import('./DriveRoute')`＋`import('@/features/drive')` → `loadDriveCanvas()`。`import()` は取得だけでなく**モジュールの評価**まで行う。運転のチャンクと 3D は gzip で約 264 KB（three・R3F・drei 含む）で、展開後は約 800 KB 前後の JS。CPU 4× のスマホでは、評価が 100 ms 台の 1 本の長いタスクになる見込み（推定。未計測）。A-2 は地図（maplibre）を操作する画面で、そこに割り込む
  - 起動の合図の `requestIdleCallback` は**メインスレッドのアイドル**であって、**ネットワークのアイドルではない**。しかもタイマーは A-2 のチャンクが解決した時点（A-2 の描画前）から数え始める。最長 2 秒で強制的に始まる。A-2 の地図のタイル・スタイル・maplibre の本体・旅程データの取得が続いている間に始まりうる。Slow 4G（下り 1.47 Mbps）では 264 KB だけで約 1.4 秒の帯域を取る
  - Chrome の `import()` は `fetchpriority` を指定できず、既定の優先度で取りに行く。地図のタイルと同じ優先度
  - 計測は `/plan` と `/drive` だけ（`measure-load.mjs`）。A-2 で先読みが動いたときの LCP や地図の完成は測っていない。R5 の合格は「Fast 4G の `/plan` と `/drive` の LCP」だけで、先読みが A-2 を遅くしないことは確かめていない
  - 重複は問題ない: `./DriveRoute`・`@/features/drive`・`load-drive-canvas.ts` は同じモジュールの map で 1 回しか読まれない。`pending` が 2 回目を止めている。失敗時は `pending = null` で次の呼び出しで読み直す。`lazy` の中の予約はルートごとに 1 回なので、A-2 に戻っても二重に予約されない
  - 先読みと A-2 の取り合いは「しおりから出発」の直前に起きる。取り合いが起きるのは回線が細いときだけ。通常の Fast 4G 以上では 264 KB は 0.3 秒未満
- 影響: 細い回線で A-2 の地図の表示が遅れる可能性。A-2 の操作中の 100 ms 級のメインスレッドのブロック
- 改善（小さい順）:
  1. 先読みを `<link rel="prefetch" as="script">`（最低優先度・評価しない）に変える。運転のチャンクは Vite がハッシュつきの immutable で配るので、HTTP キャッシュから使える。URL は `vite build --manifest` で分かる。評価は運転の画面に入るときになるが、ネットワークの待ちが消えるので十分
  2. `import()` のままなら、起動を「A-2 の地図の `load` イベントの後」に変える（maplibre の `map.once('idle')`）。タイマーの起点を A-2 の描画後にする
  3. `connection.effectiveType` が `slow-2g`・`2g` のときも先読みしない（今は `saveData` のみ。`schedulePreloadDrive`）
- 計測方法: `measure-load.mjs --paths /trip/<id>/brief` に A-2 の初期データが要る。モック API を `page.route` で差し込み、Slow 4G で「先読みあり／なし」の LCP と `map idle` の時刻を 3 回の中央値で比べる。`PerformanceObserver` の `longtask` を A-2 の間で集めて、先読みの評価のタスクの長さを出す
- 推定効果: Slow 4G の A-2 の地図の表示を数百 ms 守る（見込み）。メインスレッドの長いタスク 1 本（100 ms 台）を A-2 の操作の外に出す

### W5. `/drive` を直接開いたときの読み込みの段と、バンドル上限の検査の抜け

- 読み込みの段（`app/DriveRoute.tsx`・`DrivePage.tsx:45`）: `/drive` を直接開く・再読込するときは、入口 → DriveRoute と drive（Vite の preload で並列）→ 評価・描画 → 3D のチャンク、の順。3D のチャンクの取得は `Scene` が最初に描かれた時点で始まる。`loadDriveCanvas()` を drive の barrel の評価時（モジュールの先頭）に 1 回呼べば、描画の待ち（数十 ms）が 1 段分前倒しになる。効果は小さい（Info 扱い。やるなら 1 行）
- バンドル上限の検査（`scripts/perf/bundle-budget.mjs`）の抜け:
  1. **地図のライブラリ（maplibre）は画面の予算に入らない**。A-2 は「`OTHER_DYNAMIC` に含めて除く」ので、A-2 の予算 232 KB は maplibre を含まない。maplibre が 100 KB 増えても `all`（1,075、実測 975.8 で余裕 99 KB）に達するまで通る。maplibre のチャンクにも個別の上限（`'maplibre'` 行）が要る
  2. 上限の余裕は一律 約 1 割。`/drive` 290（実測 263.9）、3D 271（246.5）は、three の小さな追加（drei のヘルパー 1 つ）で 26 KB なので数回で使い切る。これは意図どおりだが、余裕の使われ方を報告（`--json` の出力）に残さないと、いつ何で増えたかが分からない。CI の出力に前回との差を出すか、`docs/reports/` に 1 行ずつ残す
  3. 数えるのは JS と CSS の gzip だけ。画像・フォント（Noto Sans JP を足すと数 MB）・wasm・worker（Vite は worker のバンドルを manifest に入れない版がある。`all` の注釈に「地図のワーカーを含む」とあるが、ビルドの出力フォルダの全ファイルの合計と突き合わせる検査が無い）は抜ける。`dist` の全 `.js` の合計との比較を 1 行足すと、manifest にないチャンクが検知できる
  4. 上限は gzip -9 の値。`vite preview`・本番の Vercel は gzip -6 または brotli。数 % 違うが、向きは安全側
  5. 最初のビルドを CI で毎回回す（timeout 600 秒）。`npm run build` と二重なので、可能なら既存のビルドの `dist` を渡す引数にして時間を半分にする（premature ではなく CI 時間の話）
  6. このモジュールは読み込むとビルドを走らせるので、`measure()` を export していてもテストから import できない。`main` ガード（`import.meta.url === pathToFileURL(process.argv[1]).href`）で包む
- Info 扱いの確認済みの点: `resolveKey` が共有チャンクを探して 1 件でなければ例外にする（閉じ側に倒れる）。`unknownDynamicEntries` は新しい画面の追加を止める

## Info

### I1. 運転中の rAF の記録（R1）: 負担・メモリは問題ない

- `engine.frame()` の追加は、整数 2 つの加算と `ms > 40` の比較だけ。割り当てなし（`frameTotals` は同じオブジェクトを書き換える）。`frameMs` は `number[]`（PACKED_DOUBLE）で、`push`＋`shift` は 7,200 要素（約 58 KB）。V8 の `shift` は通常ページの配列では先頭を切り詰めるだけ（large object space の 128 KB 未満）で、毎フレームのコピーは起きない。ここは drive-3d から同じ
- `frameSummary()` の `{ ...this.frameTotals }` は 2 欄のコピーで、`?fps=1` と結果の確定のときにしか呼ばれない
- `stepQuality` は毎フレーム `{ ...state }` を 1 つ作る。1 秒に 60 個の小さなオブジェクトで、若い世代の GC で消える。直すほどではない（`useRef` の中身を書き換える形にすれば 0 になる）

### I2. `?fps=1` の表示（R2）: 表示しないときは何も走らない。表示するときの負担は計測の邪魔になりうる

- `fps=1` でないとき: `FrameMeter` は `useState` の初期値の 1 回（`URLSearchParams` の解析）で `null` を返す。`setInterval` も購読も作られない。`DrivePage` が `snapshot` で再描画するたびに `FrameMeter` が呼ばれるが、比較が 1 回あるだけ
- `fps=1` のとき: 0.5 秒ごとに `summarizeFrames` が最大 7,200 個の `filter` → `map` → **比較関数つきの `sort`** をする。デスクトップで約 1〜2 ms、CPU 4× で 4〜8 ms（推定）。30 fps の 33 ms の中では 1 フレームを 40 ms 近くに押し上げうる。表示が落ちたフレームを増やす（計測の道具が計測を歪める）
- 再描画は `FrameMeterReadout` だけ。`useSyncExternalStore` の `get` はタイマーの間は同じ値を返すので、描画の連鎖は起きない。0.5 秒ごとに必ず新しいオブジェクトになるので、値が同じでも再描画する（`pre` 1 つなので無視できる）
- 改善（任意）: 並べ替えを `Float64Array.from(valid).sort()`（比較関数なしの数値順。数倍速い）にするか、窓を 1,800 フレーム（30 秒）に絞る。`measure-drive.mjs` は `?fps=1` を使わない（既定のクエリに無い）ので、現状は計測に影響しない。`--query fps=1` を足すときは、数字が歪むことを一言残す

### I3. 前の申し送り W1〜W3 を「直さない」とした判断: PC・CPU は無理がない。GPU は弱い端末の証拠にならない

- **W1（区間の境界で道路と林が同じフレームに集中）**: 実測の条件は、vsync あり・4× の早送りで 1 場面 75 秒に区間の境界を約 20 回またぐ・phone は CPU 4× 減速。境界の作り直しは決まった処理で毎回同じコストなので、20 回の標本でも最大が 33.4 ms 以内なら「スマホでも 1 フレームに収まる」と読める。A15（M2 の単一スレッドの約 1.3〜1.5 倍遅い）や Tensor（約 2.5〜3 倍遅い）に対して 4× は保守的な側。直さない判断は妥当。残る穴は 2 つ: ① CPU 減速は主スレッドだけで、GPU への転送（頂点 3,840 × 7 float のバッファのアップロード）と GC は減速しない。② 季節・路面の切り替えで全区間を作り直す経路は走行中は無い（I4 の dispose は未対応のまま）。条件が変わったら（走行中に天候が変わる経路を作る）W1 を再度見る
- **W2（葉の三角形を霧で隠れる木にも掛ける）**: M2 の GPU は頂点・フィルレートとも強く、「合格」は弱い iGPU（Intel UHD 620 級は M2 の 1/5 以下）の証拠にならない。**PC の目標は内蔵 GPU の 1440 × 900 で 60 fps** なので、ここは仕様の Deferred（Windows の iGPU）の実機が最優先。R4 の DPR の段は画素（フィルレート）には効くが、頂点（林とミラーの全頂点）には効かない。仕様に書いた「実機で 30 fps を割ったら W2 → 粒の数 → ミラーの頻度の順」は妥当。ミラーの頂点は DPR と無関係（256 × 72 の FBO）なので、DPR が 1 まで下がって足りないときは W2 を先に
- **W3（未計測）**: R3 で解消。vsync 無しの行で 1 フレームの仕事の余裕も取る設計は正しい。W3 が提案した `gl.info.render.triangles` の記録は入っていない。三角形の最大値を `measure-drive.mjs` の行に足すと、弱い GPU に当てるときの目安が数字で残る（任意）

### I4. 解像度の自動降下の他の点（問題なし）

- ミラーの 15 Hz の重いフレーム: 窓は 2 秒の平均（フレーム数と実時間）なので、60 fps で 4 フレームに 1 回 2 倍重いフレームがあっても平均は約 53 fps。45 を下回るのは、本当に遅いとき（ミラーのフレームが 1 つで 50 ms 近い）
- 出発前の画面も測る件: 3D は出発前から描いているので、遅い端末は出発前に下がる。出発前は車が止まっていて走行中より軽いので、出発前に下がるなら走行中は必ず下がる。誤って下がる側ではなく下げ損ねる側（出発前は余裕があり、走ると足りない）にずれる。その場合も走行中の窓で下がるので、実害は少ない
- `dprOf` は `window.devicePixelRatio` を使い、`Canvas` の `dpr={[1, 1.5]}` の範囲で `max(1, min(device, step))`。上限を超える値は設定しない
- 未確認: `Canvas` が再描画されるとき `dpr` の範囲を毎回 `setDpr` で当て直して降下を元に戻すか。R3F v8 の `configure` は `is.equ`（深い比較）で変化があったときだけ当てるはずだが、この worktree に `node_modules` が無く読めなかった。`DriveCanvas` の props は安定しているので再描画は稀。`AdaptiveDpr.test.tsx` に「降下後に親が再描画しても戻らない」のテストを足すと確定する
