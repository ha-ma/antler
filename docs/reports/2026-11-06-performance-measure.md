# 実測: A の性能（performance R3・R5、2026-11-06）

仕様: `docs/specs/performance/functional.md`。要件: `ch6-nfr.md`「A 性能」、`ch10-plan.md` の受け入れ基準。

## 要約

- **fps（vsync あり）**: PC（1440 × 900・DPR 2 → Canvas 2160 × 1350）の 4 場面と、スマホ相当（844 × 390・DPR 3 → Canvas 1266 × 585・CPU 4× 減速）の 4 場面が R3 の合格基準を満たした。走行中は 60 fps に張り付き、`approach` と `zone` の 33.4 ms 超は 0 だった。赤の出始め（`onset`）の 1 秒にも 33.4 ms 超は無い
- **長いフレーム**: 「もう一度」を押した直後の作り直しで 1 回ずつ、133 ms（スマホ相当。CPU を 4× 遅くした状態なので実時間では約 33 ms 相当）。走行中のフレームではない（`settle` のタグ。判定から外した）
- **初回読込（R5）**: Fast 4G ＋ CPU 4× で `/plan` の LCP は 0.91 秒、`/drive` は 1.28 秒（合格の線は 3 秒）。Slow 4G では `/plan` 2.63 秒（main は 3.80 秒）、`/drive` 3.96 秒（3 秒を超える。下に内訳）
- **GPU なし（SwiftShader、参考）**: 解像度の自動の段（R4）が DPR を 1 まで下げた（Canvas 2160 × 1350 → 1440 × 900）。それでも 10 fps（p50 100 ms）で、GPU の無い環境は対象外
- **測れていないもの**: スマホの GPU（A15・Tensor）と Windows の内蔵 GPU。どちらも M2 の GPU で描いているので、この方法では再現できない。実機の確認は仕様の Deferred に残した

## 環境

- MacBook（Apple M2）、macOS 26。Chromium 1248（Playwright 1.65 の Chrome for Testing）を新しいヘッドレスで動かした。`--mute-audio` で音は出していない
- GPU は ANGLE（Metal）の `Apple M2`。renderer の文字列は行ごとに確かめた
- 本番ビルドを `vite preview --port 5224`（gzip）で配信した。Vercel の本番は brotli なので、配る量はさらに小さい
- 計測のスクリプト: `scripts/perf/measure-drive.mjs`（fps）、`scripts/perf/measure-load.mjs`（初回読込）。測っている間は共有の鍵（`/tmp/antler-heavy.lock`）を持ち、ほかの重い処理と重ならないようにした
- ヘッドレスでは、ウィンドウに合成する工程が含まれない。1 場面 150 秒なので、長い走行での GC も見えていない（performance-analyzer W3）

## 初回読込（R5）

キャッシュは無効、画面は 844 × 390・DPR 3。LCP は 3 回の中央値で、単位は秒。

| 画面                   | 回線              | main の LCP              | この PR の後の LCP | この PR の後の JS（KB、転送量） |
| ---------------------- | ----------------- | ------------------------ | ------------------ | ------------------------------- |
| `/plan`（A-1）         | Slow 4G ＋ CPU 4× | 3.80                     | **2.63**           | 185.1（main 222.6）             |
| `/plan`                | Fast 4G ＋ CPU 4× | 1.45                     | **0.91**           | 185.1                           |
| `/plan`                | 制限なし          | 0.43                     | 0.13               | 185.1                           |
| `/drive`（出発の案内） | Slow 4G ＋ CPU 4× | 取れず（LCP の記録が 0） | 3.96               | 507（3D を含む）                |
| `/drive`               | Fast 4G ＋ CPU 4× | 2.27                     | **1.28**           | 507                             |
| `/drive`               | 制限なし          | 0.68                     | 0.19               | 507                             |
| `/t/:id`（A-7）        | Slow 4G ＋ CPU 4× | —                        | 3.60（FCP 3.02）   | 192.5                           |
| `/t/:id`               | Fast 4G ＋ CPU 4× | —                        | 1.04               | 192.5                           |

回線の条件（CDP の `Network.emulateNetworkConditions`）は 2 つ。

- Slow 4G: RTT 562.5 ms、下り 1,474.6 kbps、上り 675 kbps（Lighthouse のモバイル）
- Fast 4G: RTT 150 ms、下り 9 Mbps、上り 1.5 Mbps

**合格（R5）**: Fast 4G で `/plan` と `/drive` の LCP は 3 秒以内（0.91 秒と 1.28 秒）。

**Slow 4G で 3 秒を超えるもの**:

- `/drive`（3.96 秒）は入口と DriveRoute、drive の barrel、3D を読むまでが帯域で決まる
  - 3D（gzip 約 250 KB）は出発の案内の後に遅れて読む
  - それでも同じ回線を取り合うので、出発の案内の LCP が遅れる
  - ふつうは A-2 の間に先読みが済んでいるので、この数字は A-2 を通らずに直接開いたときのもの
- `/t/:id`（3.60 秒）は API の応答を待って描く画面で、`vite preview` では API が無い。いまの数字は「読み込めない」表示までの時間

**main からの変化**:

- `/plan` の JS は 222.6 → 185.1 KB に減った。画面ごとの遅延読込を入れ、A-1 は入口に残した
- `/drive` の Fast 4G は 2.27 → 1.28 秒に縮んだ。DriveRoute から drive を静的に読むようにして、読み込みの段を 1 つ減らした

## 限界と残したこと

- スマホの GPU と Windows の内蔵 GPU は測れていない（Deferred）。実機で `/drive?fps=1` を走り、左下の p5 を見る
- 30 fps を割ったときに見直す順は W2（霧で隠れる木）→ 粒の数 → ミラーの頻度（仕様 R4）
- 「もう一度」の作り直しは、CPU 4× で 133 ms（1 フレーム）かかる。実機で目立つようなら、区間の作り直しを複数のフレームに分ける（drive-season の W1 の続き）
- ヘッドレスでは合成の工程が入らない。1 場面 150 秒なので、長い走行の GC も見えていない
- A-2 の間の先読み（約 264 KB の取得と評価）が A-2 の操作にどれだけ響くかは、まだ測っていない（performance-analyzer W4）
