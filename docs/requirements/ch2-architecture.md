## 2. システム全体構成

> 出典: Claude Docs「EZO ROAD システム要件定義書 v1」https://claude.ai/artifact/Jr6zYHcjdSy5xEd1WaG7v8 （2026-11-03 エクスポート）。本文は原文のまま。変更は原文側で行い、再エクスポートする。


システムは A（ブラウザゲーム）と B（車載検知）の2つのプロダクトと、両者が共有する「アラートUIパッケージ」と「データループ」で構成する。構成図は Claude Design キャンバスのアートボード「B アーキテクチャ（車載検知 → スマホ通知）」を正とする。

| コンポーネント | 役割 | 技術（推奨・第9章で変更あり得る） | 実行場所 |
| --- | --- | --- | --- |
| A Web アプリ | 旅の設定・3Dドライブ・イベント・記録 | TypeScript, React, Vite, Three.js（R3F）, Zustand | ブラウザ（PC、スマホ横） |
| A API | しおり生成・イベント生成・記録保存・URL発行・キャプチャ受信 | Node.js (Hono/Express), SQLite → Postgres, S3互換ストレージ | クラウド |
| アラートUIパッケージ | 3状態の表示・音・読み上げを提供する共通ライブラリ | `@ezoroad/alert-ui`（React コンポーネント＋音源＋デザイントークン） | A の車内スマホ表示と B の PWA が同一コードを使う |
| B 検知ランタイム | カメラ取込→間引き→一次検知→二次確認→フラグ配信 | Python (jev), YOLOv8 CoreML, VLM（痑いフレームのみ）, WebSocket サーバー | 車載 Mac Mini |
| B PWA | 3状態表示と音、GPS×ゾーン判定 | アラートUIパッケージ＋Service Worker＋Geolocation | ドライバーのスマホ（Mac Mini の Wi-Fi AP に接続） |
| 鹿ゾーンDB | 多発区間ポリゴン＋月・時刻別重み | GeoJSON（道警統計・厚岸交通年鑑のキロポストを起点に手作成） | A API と B PWA が同一ファイルを読む |
| データループ | A キャプチャ＋B 検知フレーム → 匿名データセット → 再学習 → CoreML 配信 | 公開リポジトリの `dataset/` と 学習スクリプト | クラウド／ローカルGPU |

**A と B の接続点（必須）**

- A の「鹿アラート ON」は、3D車内のスマホマウントに B PWA と同一のアラートUIパッケージをレンダリングする。色・形・文字・音は同じ。
- B が送るフラグ JSON（第7章）を、A はゲーム内のイベントから合成して同じインターフェースで渡す。
- キャプチャ（A）と検知フレーム（B）は同じスキーマ（第7章 `Capture`）で保存する。
