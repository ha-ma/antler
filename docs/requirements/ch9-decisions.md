### ① ルート表示：Google Maps API か、それ以外か

対象画面：A-2（当日ルート＋鹿ゾーン）、A-7（旅全体の地図）。B は地図を表示しない（GPS × ゾーン判定のみ）。

| 案 | 内容 | 利点 | 欠点・コスト |
| --- | --- | --- | --- |
| a. Google Maps Platform | Maps JavaScript API で地図、Routes API で実ルートと所要時間 | 実道路・実所要時間。インバウンドに馴染みがある。実際の旅にそのまま使える感覚 | 2025年3月に月 $200 共通クレジットが廃止され、SKU ごとの月次無料枠（Dynamic Maps 10,000 ロード、Routes Compute Routes 10,000 件）に変わった。超過は Dynamic Maps $7 / 1,000、Routes $5〜10 / 1,000（[Woosmap](https://www.woosmap.com/blog/is-google-maps-api-free)）。API キー管理、利用規約（タイルのキャッシュ不可）、オフライン不可 |
| b. MapLibre GL JS ＋ OSM ベクタタイル | BSD ライセンスの地図ライブラリ。タイルは OpenFreeMap / MapTiler 等、ルートは OSRM / Valhalla の公開サーバーか自前 | 無料枠を気にせずデモ可能。スタイルを自由に変えられる（夜テーマ、鹿ゾーンの帯を地図スタイルに埋め込める）。自前ホスト可 | タイル提供元とルーティングサーバーを別に用意する。所要時間の精度は Google に劣る。3D 地形や衛星写真は限定（[MapLibre](https://github.com/maplibre/maplibre-gl-js)） |
| c. 独自アニメーション（現 Claude Design 案） | 道東・道央の簡略地図を SVG で描き、ルートと鹿ゾーンをアニメーション。実座標は使わず、主要地点だけ | 実装が最速。世界観に合う。鹿ゾーンの帯や日没の表現を自由に演出できる。API 費用ゼロ | 実道路・実距離ではない。地点追加のたびに手描き。旅の「実在感」が薄れる。B のゾーン判定（実 GPS）とデータが二重になる |
| d. ハイブリッド | A-2/A-7 は b（MapLibre）で実座標、演出レイヤー（鹿ゾーンの帯・日没帯・鹿アイコン）は独自 SVG を重ねる。ルート計算は OSRM、時間は固定係数で補正 | 実座標と演出を両取り。ゾーン GeoJSON を A と B で共有できる | b の準備コストはそのまま。2 系統の描画を同期させる実装が必要 |

### ② 3D アニメーションの方向性（操作性・イラスト・オブジェクトの動き）

対象画面：A-3、A-5（PC とスマホ横）。要件は右ハンドル視点、カーソル/ジャイロ追従カメラ、固定 HUD、鹿の出現パターン 5 種、PC 60 fps ・ スマホ 30 fps。

**エンジン**

| 案 | 利点 | 欠点 |
| --- | --- | --- |
| Three.js ＋ React Three Fiber（＋ drei、@react-three/rapier） | 最大のエコシステム（npm 週間 DL は Babylon の 10 倍超）。React の UI（HUD）と同じコンポーネントツリーで書ける。glTF 読込・アニメーション・ポストプロセスが揃う。WebGPU は r171 以降で自動フォールバック付き | 物理・音は別ライブラリを組み合わせる。低レベルのため車両力学は自前 |
| Babylon.js | ゲームエンジンとして物理（Havok）・音・WebGPU（v5 以降本番）が内蔵。Playground で試行が速い | バンドルが大きい（core 全体 約 1.8 MB）。React 連携は成熟度が低く、HUD との二重管理になりやすい |
| PlayCanvas | ビジュアルエディタで非エンジニアもシーンを調整できる。モバイル最適化が強い | Claude Code からのコード純粋な開発と相性が悪い。React 統合が限定 |

出典：[Three.js vs Babylon.js vs PlayCanvas（Utsubo）](https://www.utsubo.com/blog/threejs-vs-babylonjs-vs-playcanvas-comparison)、[three.js vs R3F vs Babylon.js 2026（pkgpulse）](https://www.pkgpulse.com/guides/threejs-vs-react-three-fiber-vs-babylonjs-3d-webgl-2026)。前者は Three.js を主に使う制作会社の記事。

**操作性**

| 案 | 内容 | 向き不向き |
| --- | --- | --- |
| A. アーケード（現案） | WASD で即応。車は車線に緩く吸着。ブレーキは制動距離のカーブだけリアル | 教育・瞬発力に向く。「鹿を見つけて踏む」に集中できる |
| B. セミリアル | ステア角・スロットル・グリップ（圧雪で滑る）を簡易モデルで | 圧雪路の恐ろしさが伝わるが、左ハンドル圏のインバウンドが操作で足をとられる |
| C. オンレール | 車はルートを自動走行。プレイヤーは視線・ブレーキ・車線内の左右だけ | 最も安全でスマホでも成立。「運転している」感が減る |

**イラストの方向性**（車内・風景はアニメ調でよい。鹿は③）

| 案 | 内容 | 制作コスト |
| --- | --- | --- |
| ローポリ＋フラットシェーディング | Claude Design の現案に近い。車内・道路・雪原を最小ポリゴンで。フォグと薄暮の色で雰囲気を出す | 最低。アセットを自作できる |
| スタイライズド・リアル（PBR＋簡略マテリアル） | 圧雪とヘッドライトの光を PBR で。車内は実車に近いプロポーション | 中。車内モデルはストアで購入か CC0 |
| フォトリアル | 実写テクスチャと HDRI | 1 週間では困難。ブラウザでの fps も厳しい |

**オブジェクトの動き**：鹿 5 パターン（路肩静止、林縁で目の反射のみ、車線横断、群れ、車前で立ちすくみ）をスプライン軌跡＋アニメーションクリップ（idle / walk / run / look）で。対向車・先行車はレール走行。雪・ワイパー・曇りはフルスクリーンシェーダー。鹿の目の反射（テーヘート）はヘッドライト方向との内積で強度を決める（薄暮では最初に見える手がかりにする）。

**推奨**：Three.js ＋ R3F、操作は A（アーケード）でスマホは C に切替可、イラストはローポリ＋フラットを基調にして鹿とヘッドライトだけ PBR。理由：HUD と 3D を 1 つの React ツリーで書け、Claude Code が最も多くの参考実装を持つ。

### ③ 鹿などイラストレーションのクオリティアップ

要件：鹿は「学習モデルが見て実物の確認に役立つ」水準。形・プロポーション・姿勢・目の反射が実物に近いこと。毛の質感よりもシルエットと薄暮での見え方が重要。

| 案 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| a. ストアのリアル系リグ済みモデルを購入 | Sketchfab / CGTrader / Fab の「Realistic Deer Buck」等。glTF でアニメーション付きが多い | 品質が確定している。当日に組み込める | ライセンスがアセットごとに異なり、公開リポジトリと教師データ配布に使えないものが多い。ニホンジカ（エゾシカ）ではなくオジロジカ・アカシカが大半 |
| b. CC0 ローポリを出発点にして自前で仕上げ | Quaternius 等の CC0 パックは牛・馬・ラマ等で、鹿は含まれない（[Quaternius](https://quaternius.itch.io/lowpoly-animated-animals)）。馬のリグを流用し鹿を Blender で造形 | 権利クリア。エゾシナの体格（肩高 約 1 m、角の形）に合わせられる | Blender 作業が必要。品質は作業量次第 |
| c. AI 3D 生成（Meshy / Tripo） | 写真からメッシュを生成。Meshy は自動リグ・アニメーションと GLB 出力。Tripo はトポロジが整いリギング向き（[SelfCAD](https://www.selfcad.com/blog/meshy-vs-tripo)） | 最速でエゾシカの形に寄せられる。複数バリアント（牝・牛・若齢）を増やしやすい | メッシュは「そのままプロ用途には不十分」とするレビューがあり、Blender での修正前提。生成物のライセンスと学習データ配布の可否を各サービスの規約で確認する |
| d. 調査走行の実写を混ぜる | 週末の調査走行で撮った実写鹿を、A では「発見後のキャプチャ比較」と教師データに、B では学習に使う | 合成データは実データを少量混ぜると実画像性能が大きく上がる（シマウマ検出の研究では合成のみは実データ学習より mAP50 で約 5 ポイント低いが、実データを足すと最良。[arXiv 2305.00432](https://arxiv.org/html/2305.00432v2)） | 撮れるかは運次第。モデルの品質そのものは上がらない |

**教師データとしての品質を上げる実装上の工夫**（どの案でも有効）：カメラを B の Web カメラと同じ画角・高さにする。時刻・天候・距離・姿勢・当たり最大をランダム化する（ドメインランダマイゼーション）。キャプチャは保存時に B と同じ解像度（640×480）にも落として保存する。近距離のキャプチャを多くする（前述の研究でも近距離の合成画像が効いた）。

**推奨**：MVP は c（AI 生成）でエゾシカの写真から 3 バリアントを作り Blender で角・耳・臀の白斑を直す。并行して d（実写）を集める。a はライセンスが公開リポジトリ要件と衝突しやすく、b は時間が足りない。
