# 障害耐性: plan-trip（A-1 旅をつくる・Claude がしおりを仕上げる）

方針: **Claude の文が作れなければ旅を保存しない（代わりの文を作らない。roadmap「フォールバックなし」）。** 入力は端末に残るので、利用者は同じ内容で「もう一度」押せる。
しおり（days）とリスクは端末でも api でも決定的に計算できるので、Claude が止まっても A-1 の画面は動き続ける。

## Concurrency / Idempotency

| 対象                 | 並行実行されうるか                   | 二重実行されうるか                     | 冪等性要件                                                          | 実装方針                                                                                                                                                                                                                                                                                |
| -------------------- | ------------------------------------ | -------------------------------------- | ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| POST /api/trips      | 別の利用者から同時に来る             | 「決める」の二重押し・時間切れ後の再送 | **必須**（同じ冪等キーで旅を 2 つ作らない・Claude を 2 回呼ばない） | `trip_requests` 表に（key 主キー、body のハッシュ、状態 pending / done / failed、trip_id）を先に INSERT。主キー違反なら既存の行を見て、done → 保存済みの旅を返す、pending → 409 IN_PROGRESS、failed → 状態を pending に戻して作り直す、body のハッシュが違う → 409 IDEMPOTENCY_MISMATCH |
| 1 日の上限の数え上げ | 同時の作成で上限をわずかに超えうる   | N/A: 数えるだけ                        | 不要（上限は費用の目安。数件の超過は許す）                          | Claude を呼ぶたびに（作り直しの 2 回目も）`trip_writer_calls` に 1 行足し、呼ぶ前に当日の行数を `CLAUDE_DAILY_CALL_LIMIT` と比べる。再送で保存済みの旅を返すときは呼ばないので数えない。同時の呼び出しは `CLAUDE_MAX_CONCURRENT_CALLS` まで（プロセス内）。厳密な同時制御はしない       |
| id の採番            | 同時に同じ id を引く確率は無視できる | N/A: 毎回新規                          | 不要                                                                | unique 制約 ＋ 衝突時に作り直し（3 回まで）                                                                                                                                                                                                                                             |

## トランザクション境界

### 操作: POST /api/trips

1. 入力の検証（Claude・DB の前）
2. 冪等キーの行を INSERT（pending）— 単独のトランザクション。ここで 2 回目の要求を止める（done なら保存済みの旅を返して終わり）
3. 1 日の上限の確認（超えていれば冪等キーを failed にして 429。Claude を呼ばない）
4. しおり・リスクの計算（純粋関数）
5. Claude の呼び出し（トランザクションの外。30 秒まで）
6. TripPlan・TripDetails・ownerToken のハッシュを INSERT し、冪等キーの行を done と trip_id に更新 — 1 つのトランザクション
7. 5 か 6 が失敗 → 冪等キーの行を failed に更新（旅の行は残さない）

ownerToken は `HMAC(OWNER_TOKEN_SECRET, 冪等キー)`。同じキーの再送に同じトークンを返せて、トークンもキーも保存しない（保存するのはトークンのハッシュだけ）。キーがログに残ってもトークンは計算できない（2026-11-03、推奨で決定）。

## 競合 / レース対策

### 同じ冪等キーの同時の 2 要求

主キー（key）の INSERT で片方だけが通る。もう片方は主キー違反になり、行が pending なので 409 IN_PROGRESS を返す。Claude は 1 回しか呼ばれない。

### pending のまま api が落ちた

pending の行は作成から 2 分を過ぎたら failed とみなし、同じキーの再送で作り直す。
