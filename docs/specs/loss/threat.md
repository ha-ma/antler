# 脅威: loss（A-6 喪失・Claude が「失ったもの」を書く）

この feature の HTTP の操作は `POST /api/trips/:id/losses` の 1 つ（喪失文を作る・保存済みなら返す）。画面が読むしおりは brief-map の `GET /api/trips/:id/day/:n`（その threat.md が正。この feature では変えない）。
守るものは「Claude の費用（記述子を変えて何度も呼ばせる濫用）」「保存した文の書き換え（Mass Assignment）」「所有者の印（ownerTokenHash）を出さないこと」の 3 つ。

旅の ID を知る人が喪失文を作れる（所有者トークンを求めない。推奨で決定）。
理由: A-6 は登録なしで最後まで通る（付録 A #9）。旅の ID は英数 8 文字で推測できない（brief-map の threat.md と同じ方針）。喪失文は旅の中身から決まる短い文で、個人を特定しない。作れても旅そのもの（TripPlan）は変わらない。

**残るリスク**: ID を知る人は、その旅に事実と違う喪失文（例: 走っていない日の衝突、偽の OFF）を保存できる。文は旅の中身から決まり、保存した文を読む API はこの feature に無い（A-6 は自分の URL の記述子で読む）。A-7 に出すときの扱いは record が決める（functional.md の Deferred）。

**残るリスク（security-auditor M-1・M-2、`docs/reports/2026-11-04-security-auditor-loss.md`）**: (1) 1 日の上限は plan-trip と丸ごと共有で、loss 専用の下位の枠が無い。1 つの IP が IP の上限の範囲で喪失文を作り続けると、当日の旅の作成も 429 になりうる（費用は上限で頭打ち）。公開して濫用が見えたら、loss に全体の一部（例 25%）までの別の数え上げを置く。(2) ID を知る人は記述子の組み合わせで旅の 20 件を埋められ、本人の A-6 の文の欄が LOSS_LIMIT になる（4 指標・しおり・統計カードは端末で出るので画面は失われない）。

**✅ (公開) の理由**: 付録 A #9「A が登録なしで最後まで」。旅の ID は推測困難で、作れるのは旅の中身から決まる短い文だけ。費用はレート制限・1 日の上限・同時の枠で抑える（plan-trip と同じ数え上げを共有する）。

## IDOR / Mass Assignment チェック

- **IDOR**: 対象は URL の `id` で決まる。所有者で絞らない（上の理由）。無い id と形の違う id は同じ 404
- **クライアントから受け取るフィールド**: パスの `id`、body の `day`・`leg`・`at`・`alertEnabled`・`achievedStops`
- **サーバー側で設定するフィールド**: `story`（Claude の文）、`createdAt`、保存の鍵（記述子のハッシュ）、`tripId`（パスから）
- **クライアントから受け取ってはいけないフィールド**: `story`・`tripId`（body）・`createdAt`・鍵・`ownerToken`
- **検証方法**: zod の strictObject（知らない欄は 400）。範囲（日・移動・暦日・その日の楽しみ）はドメインの `checkCollision` が保存したしおりと突き合わせる。応答は `{ loss: { tripId, story, createdAt } }` を明示して組み立てる
