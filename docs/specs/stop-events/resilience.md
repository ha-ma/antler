# 障害耐性: stop-events（A-4 観光スポット・Claude の出来事の文・イベントログ）

方針: **Claude の文が作れなければ束を保存しない（代わりの文を作らない。roadmap「フォールバックなし」）。** 束は日ごとに 1 回だけ作り、作れなかった日は次の POST で作り直す。
運転は束が無くても続く（A-4 を出さないだけ。drive-link が決める）。イベントログは再送で重複しない。

## Concurrency / Idempotency

| 対象                         | 並行実行されうるか                        | 二重実行されうるか | 冪等性要件                                                    | 実装方針                                                                                                                                                                                                                                                                                                                                             |
| ---------------------------- | ----------------------------------------- | ------------------ | ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 束の POST                    | 同じ旅・同じ日を 2 つのタブが同時に開く   | 再読み込み・再試行 | **必須**（同じ日の束を 2 回作らない・Claude を 2 回呼ばない） | `stop_decks` 表に（trip_id, day）主キーで pending の行を先に INSERT。主キー違反なら既存の行を見て、done → 保存済みを返す（200）、pending → 409 IN_PROGRESS、failed・2 分を過ぎた pending → 読んだときの status と updated_at のままなら pending に戻して作り直す（同時の作り直しは片方だけが通る）。冪等キーのヘッダは要らない（旅と日が自然なキー） |
| イベントの POST              | 同じ run の送信が重なる（再送と次の送信） | 通信の失敗後の再送 | **必須**（同じイベントを 2 行にしない）                       | （trip_id, run_id, seq）主キー。既存の行を読んで中身（正規化した JSON）を比べ、同じ → 重複、違う → 409 で全件を入れない。新しい行は 1 つの INSERT … ON CONFLICT DO NOTHING で入れる（SQLite の 1 文は原子的）。同じ seq を違う中身で同時に送るのは端末の誤りで、先に入ったほうが残る（Info）                                                         |
| 旅のイベントの上限の数え上げ | 同時の POST で 5,000 件をわずかに超えうる | N/A: 数えるだけ    | 不要（上限は濫用の目安）                                      | 入れる前に旅の行数を数え、足すと 5,000 件を超えるなら 409                                                                                                                                                                                                                                                                                            |
| 1 日の上限の数え上げ         | plan-trip の作成と同時に数えうる          | N/A: 数えるだけ    | 不要（上限は費用の目安。数件の超過は許す）                    | plan-trip の `countWriterCall`（当日の通し番号）を、Claude を呼ぶたびに使う                                                                                                                                                                                                                                                                          |

## トランザクション境界

### 操作: POST /api/trips/:id/day/:n/stop-deck

1. パスの検証、旅の読み出し（無ければ 404）、トークンの照合（違えば 403）、日の範囲（無ければ 404）— Claude・書き込みの前
2. 束の行を INSERT（pending）— 単独の文。done なら保存済みを返して終わり
3. DayPlan と束の組み立て（純粋関数。外部通信なし）
4. 同時呼び出しの枠を取り、Claude を呼ぶ（トランザクションの外。呼ぶたびに 1 日の上限を数える）
5. 束と文を UPDATE して done — 単独の文
6. 3〜5 が失敗 → 束の行を failed に UPDATE

### 操作: POST /api/trips/:id/events

1. パスと body の検証（zod）、旅の読み出し、トークンの照合
2. choice の解決（保存した束を読む。無い・知らない id → 400）
3. 既存の行の読み出しと比較（重複 / 衝突）、旅の行数の確認（上限）
4. 新しい行を 1 つの INSERT 文で入れる

## 競合 / レース対策

### 同じ日の束の同時の 2 要求

（trip_id, day）主キーの INSERT で片方だけが通る。もう片方は行が pending なので 409 IN_PROGRESS。端末（useStopDeck）は 409 を 5 秒あけて 12 回まで（60 秒）待ち直す（生成は最悪 45 秒 × 2 回）。

### pending のまま api が落ちた

pending の行は更新から 2 分を過ぎたら作り直せる（plan-trip と同じ。生成は最悪 90 秒なので、まだ動いている生成を横取りしない）。
done・failed の UPDATE は「自分が立てた pending（status と updated_at）のまま」を条件にする。作り直しに取られた古い生成は書かない（CONC-33）。
