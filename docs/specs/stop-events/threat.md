# 脅威: stop-events（A-4 観光スポット・Claude の出来事の文・イベントログ）

この feature の HTTP の操作は `POST /api/trips/:id/day/:n/stop-deck`（束の生成。Claude の費用）と `POST /api/trips/:id/events`（イベントログ。record の材料）の 2 つ。
守るものは「Claude の費用」「他人の記録の正しさ（偽の衝突を書かせない）」「保存する欄（端末の計算値を信じない）」の 3 つ。

旅の id は記録 `/t/{id}`（A7-1、ログインなし）で共有される公開の値なので、書き込みの権利にはしない。旅を作った端末だけが持つ ownerToken（plan-trip R7。HMAC で作り、api はハッシュだけを持つ）をヘッダ `Authorization: Bearer` で求める（推奨で決定。ownerToken の役割を「削除」から「その旅への書き込み」に広げる。record に PR で知らせる）。

**トークンを持たない端末（共有リンクから開いた人）**: 束を受け取れず（A-4 を出さない）、イベントも送らない。運転（A-3・A-5）は束なしで続けられる。「見る人は走れるが、記録には書けない」を意図した挙動とする。

**記録は自己申告**: 所有者は自分の旅の記録に、遭遇・回避・衝突を自由に書ける（端末の値。choice だけは束から写す）。ゲームの記録なので受け入れる。守るのは「他人の記録に書かせない」こと。

**存在の秘匿**: 旅が無い・id の形が違う → 404（brief-map と同じ。区別しない）。旅はあるがトークンが違う → 403。旅の存在は GET（brief-map）で既に公開なので、403 で漏れる情報は増えない。

## IDOR / Mass Assignment チェック

### POST /api/trips/:id/day/:n/stop-deck

- **クライアントから受け取るフィールド**: パスの id・n、ヘッダ Authorization: Bearer
- **サーバー側で設定するフィールド**: 束の全部（場面・選択肢・時刻・光・失うもの・支出）と Claude の文
- **クライアントから受け取ってはいけないフィールド**: 束と文の全部（body は読まない）
- **検証方法**: n は 1 以上の整数（zod）。トークンは 16 進 64 文字（形が違えば 403）。旅の行の ownerTokenHash と、受けたトークンの SHA-256 を比べる

### POST /api/trips/:id/events

- **クライアントから受け取るフィールド**: runId（UUID v4）、alertEnabled、events[]（seq・day・at・leg・km と kind ごとの欄。R10）
- **サーバー側で設定するフィールド**: tripId（パス）、receivedAt、choice の計算値（sceneKind・choiceKind・delayMin・endsDay・light・lostJPY・lostWeight・lostPleasures。保存した束から写す）
- **クライアントから受け取ってはいけないフィールド**: tripId（body）、receivedAt、choice の計算値、緯度経度（位置は leg・km だけ）
- **検証方法**: zod の strictObject と kind の判別共用体。知らない欄は 400。choice の sceneId・choiceId は保存した束にあるものだけ。day は旅の日数以内
