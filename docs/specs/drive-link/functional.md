# 仕様: drive-link（A-1・A-2 で作った旅を運転 A-3 へ渡す）

## 概要

A-2（`/trip/:id/brief`、brief-map）の「エンジンをかける」は `/drive?trip={id}&day={n}(&alert=off)` へ移る（brief-map R8）。
この feature で `/drive` がその URL を読み、`GET /api/trips/:id/day/:n`（brief-map R5）の `DayPlan` から運転の場面（`DriveScenario`）を作って、その旅のその日のルートを走る。
同じ旅・同じ日なら、同じ道・同じ当日の条件・同じ鹿になる（A6-4 の再生の前提）。`trip` の無い `/drive` は、drive-3d の見本の場面のまま残す（開発用）。
要件: ch3 A2-2（鹿アラートの ON/OFF）・A2-3（当日の条件）・A3-1〜A3-6、A6-4（同じシードで再生）、ch7（TripPlan・API）、plan-trip R10（TripPlan は作成後に変えない。ON/OFF は走行の記録の側）。
前の feature: docs/specs/drive-3d/functional.md（場面・シミュレーション・HUD）、docs/specs/brief-map/functional.md（R4 当日の条件、R5 API、R8 受け渡し）。

**Tier 1**: 認可（API は ID を知る人が読める。brief-map の threat.md のまま）・永続化・外部への副作用・並行性に触れない。API は読むだけ。

**範囲外**: A-4 の立ち寄り（stop-events。この feature はその日の移動の区切りの道のりを場面に残すだけ）、A-6 喪失・A-7 記録の画面（loss・record。この feature は走行の結果の形を渡すだけ）、`/drive` のチャンクの先読み（brief-map の Deferred。暫定のまま）、1 日の移動が長いときの時間の圧縮（16× のまま）。

## Example Map

Story: A-1 で自分の旅をつくった旅行者として、A-2 で「エンジンをかける」を押したら、その日のルートと条件のまま運転したい。やり直しても同じ道・同じ鹿で。

- R1: 入口は `/drive?trip={id}&day={n}(&alert=off)`
  - `trip` が無い → drive-3d の見本の場面（開発用。URL の `?alert=off` は今まで通り効く）
  - `day` が無い・読めない → 1（brief-map の `parseDay` と同じ規則: 1〜999 の整数だけ）
  - `trip` の形が違う（英数 4〜16 文字でない）→ 読みに行かずに「旅が見つかりません」
- R2: その日の行程を `GET /api/trips/:id/day/:n` から読む（TanStack Query）
  - 応答は `TripPlanSchema`・`TripDetailsSchema`・`DayPlanSchema` で形を確かめてから使う
  - 再試行は通信の失敗と 5xx だけ 1 回（brief-map の useTripDay と同じ決まり）。10 秒で時間切れ
  - 読み込み中は出発の案内の代わりに「旅を読み込んでいます」
  - 失敗の案内は brief-map のエラーの表と同じ分け方:
    - 404 `TRIP_NOT_FOUND` → 「旅が見つかりません」と A-1 へ
    - 404 `DAY_NOT_FOUND` → 「その日はありません」と D1 の A-2 へ
    - 409 `ITINERARY_CHANGED` → 「この旅は古い形式です」と A-1 へ（読み直しても直らないので「もう一度」を出さない）
    - 429 `RATE_LIMITED` → 「少し待ってもう一度」と「もう一度」
    - そのほか（通信・5xx・形の違う応答）→ 「読み込めませんでした」と「もう一度」と A-2 へ
  - 移動の無い日（`legs` が空）→ 「この日は移動がありません」と、その日の A-2 へのリンク
- R3: `DayPlan` から運転の場面を作る（純粋関数 `scenarioFromDay`）
  - ルート: 移動ごとに `route` をなめらかにして 20 m ごとに打ち直し、順につなぐ。つなぎ目はなめらかにしない（前の移動の終点と次の移動の始点が離れていれば直線で埋める。宿で折り返しても輪やトゲを作らない）
  - 出発時刻: 最初の移動の `departAt`。旅程: `plan`。日: `n`
  - 2 つ目以降の移動は、その移動の始まりに着いた時点で、時計をその移動の `departAt` まで進める（しおりの立ち寄り・待ちの時間。既に過ぎていれば進めない）。A-2 が「薄暮に通過」と出したゾーンを、運転でも同じ光の頃に通る。立ち寄りの画面は stop-events
  - 当日の条件: `conditions.weather`・`surface`・`windowFog` をそのまま使う（brief-map R4 が drive と同じ語彙で作っている）
  - 移動の区切り（2 つ目以降の移動の始まりの道のり m と `departAt`）、出発地・到着地、移動の距離の合計（`distanceKm` の和。A-2 の要約と同じ数）を場面に残す
  - 鹿アラート: URL の `alert` の最初の値がちょうど `off` なら OFF、それ以外は ON（brief-map の `driveHref` が書く形）。`plan.alertEnabled` は見ない（plan-trip R10: TripPlan は作成時の初期値のまま。ON/OFF は走行の記録の側に持つ）
- R4: 同じ旅・同じ日なら同じ場面
  - 鹿の候補と検知の乱数の種は `deriveSeed(旅のシード, "drive:" + 日)`。日が違えば違う鹿、同じ日なら同じ鹿
  - ルート・条件は API が (旅, 日, データの版) から決めるので、同じ応答なら同じ場面（`scenarioFromDay` は純粋関数）
  - 「同じシードでもう一度」は API を読み直さずに同じ場面を最初から走る
  - 見本の場面も同じ決まりで作る（種は `deriveSeed(918273, "drive:2")`、窓の曇りは 4 人・曇りの light）。drive-3d の見本の結果（鹿の配置・検知の確率）はここで変わるので、drive-3d のテストの期待値を新しい決まりに合わせる
- R5: ゾーン（鹿ゾーンの区間）の正は、sim に同梱した zones.geojson を `planRoute` にかけたもの
  - `source: "straight"`（直線で引いた概算のルート）の移動では区間を作らない（brief-map R1: 直線ではゾーンを判定しない。A-2 に出ないゾーンで琥珀にも鹿にもしない）
  - API の `DayPlan.zones` とは、区間の数とゾーンの id が一致し、入口の道のりの差が 0.5 km 以内であることをテストで確かめる（なめらかにした線は API の間引いた線より少し長い）
  - `day.data.zones`（API のゾーン DB の hash）が同梱のものと違えば、警告をログに残して同梱のものを使う（api と sim のデプロイがずれたとき。画面は止めない）
  - ゾーン状態は車の道のり s から直接出す（区間を二分探索。s / 1000）。0.1 秒ごとに `measureAlongRoute` で全線分（280 km なら 20 m 間隔で 1 万 4 千本）を走査しない（performance-analyzer W-1）
- R6: 車内の曇りは当日の条件の `windowFog` から（none 1.0・light 0.95・medium 0.9・heavy 0.85 を検知の確率に掛ける）。drive-3d の人数による係数を置き換える
- R7: 出発の案内に、旅のタイトル、日（D2 など）、出発地 → 到着地（地点のマスターの名前）、距離（`distanceKm` の和）、天候・路面を出す。A-2 へ戻るリンク（アラートの状態を引き継ぐ）
- R8: 走行の結果（`DriveResult`）を barrel から出す。A-6・A-7（loss・record）が使う。この feature では作って出すだけ（画面は後の feature）
  - 中身: 旅の id・日・種・`day.data`（データの版。A6-4 の再生で同じ版か確かめる）・鹿アラートの ON/OFF・結果（collided / completed）・終わった時点の道のり s・何本目の移動か・シミュレーションの時刻（JST）・衝突した鹿の id・遭遇の記録・入力の列（時刻つき。A-6 の「衝突の 3 秒前を見る」用）・フレームの要約
  - 結果は衝突か完走のときだけ作る。途中でページを離れたときは作らない
  - 終了の帯に、旅があるときは「ブリーフィングに戻る」（その日の A-2。アラートの状態を引き継ぐ）

推奨で決定（CLAUDE.md の方針。PR にも書く）: R1 の `trip` が無いときは見本の場面、R2 の画面の文言と再試行、R3 の移動ごとになめらかにしてつなぐ・時計を `departAt` まで進める・アラートは URL だけで決める、R4 の種の作り方（見本の結果も変わる）、R5 のゾーンの正は同梱の DB・直線の移動に区間を作らない・s から出す、R6 の曇りの係数、R8 の結果の形。
spec-adversary の指摘（C1〜C3・M1〜M5・m1〜m2、2026-11-04）は上の各ルールに取り込んだ。

## ユースケース

### UC-1: 入口（R1）

- **Given**: `/drive` の URL
- **When**: 画面を開く
- **Then**: `trip` の有無と形で、見本の場面・読み込み・「旅が見つかりません」に分かれる

### UC-2: 読み込み（R2）

- **Given**: 旅の id と日
- **When**: API から読む
- **Then**: 形を確かめた応答だけを使い、失敗はその種類に合わせて案内する

### UC-3: 場面（R3・R4・R6）

- **Given**: `DayPlan` と `TripPlan`、URL の `alert`
- **When**: 場面を作る
- **Then**: その日のルート・時刻・条件・アラートで走り、同じ入力なら同じ場面・同じ鹿

### UC-4: ゾーン状態（R5）

- **Given**: 長いルートと車の道のり
- **When**: 0.1 秒ごとにゾーン状態を出す
- **Then**: 道のりから区間を引き、全線分を走査しない

### UC-5: 出発の案内と結果（R7・R8）

- **Given**: 旅の場面
- **When**: 出発前・終了後
- **Then**: 旅のタイトル・日・区間が出て、終わったら結果を渡し、A-2 へ戻れる
