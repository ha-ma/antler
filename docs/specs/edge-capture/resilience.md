# 障害耐性: edge-capture（検知フレームの保存・走行後の同意・アップロード）

方針: **保存は赤の経路の外にあり、失敗しても検知（赤）を止めない。** 溢れたら捨てて数える（保存より検知が先）。
送信は「同意が edge に残り、送れなかった分は未送信のまま次回に続きから」。同じ `id` の再送は冪等（同じ中身なら何度でも成功、違えば 409）。
回線が無い・edge が見つからない・api が落ちている、どれでも利用者の操作（通知・接続）は変わらない。

## Concurrency / Idempotency

| 対象                               | 並行実行されうるか                                       | 二重実行されうるか                        | 冪等性要件                                                                 | 実装方針                                                                                                                                                                                                                                                        |
| ---------------------------------- | -------------------------------------------------------- | ----------------------------------------- | -------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| api の `POST /api/captures`        | 別の端末から同時に来る。同じ `id` が同時に来ることもある | 回線切れの再送・「もう一度」              | **必須**（同じ `id`・同じ中身なら 1 つだけ保存し何度でも成功。違えば 409） | 画像を `{id}-{sha256 先頭12桁}.{ext}` で一時ファイルからハードリンク（`EEXIST` は同じ内容なので無視）→ JSON を一時ファイルからハードリンクで作る（存在すれば失敗 = 先に取った方の勝ち）。失敗した側は既存を読んで本文のハッシュを比べ、同じなら 200、違えば 409 |
| api の保存件数                     | 同時に上限をわずかに超えうる                             | N/A: 数えるだけ                           | 不要（上限は容量の目安。数件の超過は許す）                                 | 起動時に 1 回数え、保存のたびに増やすメモリの数                                                                                                                                                                                                                 |
| edge の保存（recorder → ワーカー） | 検知のスレッドとワーカーのスレッドが並ぶ                 | N/A: 1 フレーム 1 回                      | 不要                                                                       | 有界のキュー 1 本・ワーカー 1 つ。`offer` は待たない                                                                                                                                                                                                            |
| edge の `l1Probs` の書き足し       | ワーカーの保存と、イベントループの L1 の答えが並ぶ       | N/A: 答えごとに付けるのは未設定のものだけ | 付けるのは一度だけ（すでにあれば付けない）                                 | 保存の記録（メモリ）をロックで守り、JSON の差し替えは `os.replace`                                                                                                                                                                                              |
| edge の同意・送信済みの更新        | PWA の 2 つのタブから同時に来る                          | 「もう一度」                              | 必須（同じ値を何度書いても同じ）                                           | ロックの中で JSON を読んで書き換え。送信済みのしるしは空ファイルの作成（作成済みなら何もしない）                                                                                                                                                                |
| id の採番（edge）                  | N/A: 1 つのワーカーが採番                                | 乱数 48 ビットの衝突（無視できる）        | 不要                                                                       | 衝突したら（ファイルが既にある）作り直し                                                                                                                                                                                                                        |

## トランザクション境界

### 操作: edge の保存（1 枚）

1. `offer`（検知のスレッド）: 条件・間隔・上限を確かめ、画像を縮めてコピーし、キューに入れる（ここまで。待たない）
2. ワーカー: JPEG に変換 → 一時ファイルに画像 → `os.replace` で `{id}.jpg` → 一時ファイルに JSON → `os.replace` で `{id}.json`（**JSON が最後 = 完成のしるし**）
3. 1 か 2 のどこで失敗しても完成品は増えない。画像だけ残ったものは次の起動で消す

### 操作: POST /api/captures

1. 本文の大きさ → 検証（スキーマ・同意・画像）— 何も書かない
2. 同じ `id` を探す（あれば本文のハッシュを比べて 200 か 409 で終わる）
3. 件数の確認（503）
4. 画像を一時ファイルに書き、ハードリンクで `{id}-{hash}.{ext}` に（`EEXIST` は無視）
5. JSON を一時ファイルに書き、ハードリンクで `{id}.json` に（存在すれば失敗。先に取った方の勝ち）
6. 一時ファイルを消す。5 が失敗（存在）したら、既存を読んで比べ、4 で作った画像が不要なら消す

### 操作: PWA の送信

1. edge に同意を書く（OFF なら終わり）
2. 1 件ずつ: 画像を取る → api へ POST → 成功なら edge に送信済み
3. 途中で止まっても、次回は未送信のものだけが一覧に残るので続きから

## 競合 / レース対策

### 同じ `id` の同時の 2 要求（api）

JSON のハードリンクで片方だけが通る。負けた側は既存の JSON を読み、本文のハッシュが同じなら 200（Idempotent-Replayed）、違えば 409。読めなければ（勝った側がまだ書いていない）409 を返し、再送で解決する。

### 保存の途中で api が落ちた

画像だけ残る（JSON が無いので完成品ではない）。同じ `id`・同じ中身の再送は画像の `EEXIST` を無視して JSON を作る。中身が違う再送は、別の名前（hash 違い）の画像で作る（古い画像は孤児のまま。運用で掃除する。Deferred）。

### 検知と保存の競合（edge）

保存は検知のスレッドを待たせない（有界キュー）。`on_result` の中で I/O をしない。`wrap` は結果を下流に渡したあとで `offer` を呼ぶ。

## 観測要件（APM 閾値・監視）

| 操作                                 | 目安応答時間          | 警告閾値 | 監視方法                                                       |
| ------------------------------------ | --------------------- | -------- | -------------------------------------------------------------- |
| edge の `offer`（検知のスレッド）    | 1 ms 未満             | 5 ms     | テストで 1 フレームの所要を計る。超えたら `capture.slow_offer` |
| edge の 1 枚の保存（変換＋書き込み） | 30 ms 未満            | 200 ms   | `capture.saved` の `encode_ms`・`write_ms`                     |
| api の `POST /api/captures`          | 100 ms 未満           | 1 秒     | logger.info（`capture.received`、所要 ms、画像の大きさ）       |
| edge の `GET /captures`              | 50 ms 未満（2000 件） | 500 ms   | `capture.http` の所要 ms                                       |
